# 메인 화면 백엔드 연결 설계

> 2026-11-22 · 작성 : Claude Code (Jongeume 와 협의) · 상태 : **승인 (Jongeume, 11-22)**
> 저장소 : `KCCI-Hackathon/gemini` · 기준 : PR #1 (`frontend/ui-development`) 이 dev 에 머지된 상태

**한 줄 요약 : 새 메인 화면(Pathfinder Planner)은 그대로 두고, 중복수혜 판정과 AI 계획을 백엔드 결과로 채운다. 프론트와 백엔드가 겹치는 판정은 백엔드가 맡는다. 백엔드 판정 코드는 고치지 않는다.**

---

## 1. 왜 하나

- PR #1 이 머지되면 메인(`/`) 은 새 Planner 화면이 된다.
- 새 화면은 `/api/judge` 응답 중 `plannerV2`(프론트가 만든 판정) 만 읽는다.
- 그래서 백엔드 · 에이전트 작업이 메인 화면에서 거의 안 보인다.
	- 중복수혜 검증 에이전트 결과 (T1–T13, 송하우)
	- 개인 수혜 상태 (`benefits`)
	- AI 계획 (`/api/plan`, AG-02~07)
- 공모전 시연에서 **중복수혜 판정과 AI 계획 둘 다** 메인 화면에서 보여야 한다. (Jongeume)

## 2. 목표 · 하지 않을 것 · 실패로 볼 것

| 구분 | 내용 |
|---|---|
| 목표 | 메인 화면 카드 · 상세 · 비교 · 교체 · 에이전트 패널에 백엔드 중복수혜 판정이 나온다 |
| 목표 | 에이전트 패널에서 AI 계획을 받아 보드의 "AI 추천 경로 보기" 에 표시한다 |
| 목표 | 프론트와 백엔드가 겹치는 판정(실제 수혜 충돌, 담은 정책끼리 충돌)은 백엔드 결과 하나만 쓴다 |
| 하지 않을 것 | 백엔드 판정 코드 수정 — `lib/judge/overlap.ts`, `lib/judge/index.ts`, `lib/data/overlap.ts`, `scripts/overlap/*`, `lib/plan/handler.ts` 의 검증 로직 |
| 하지 않을 것 | 새 화면 · 새 메뉴 추가. 프론트 명세(`docs/superpowers/specs/2026-11-21-pathfinder.md`) 의 화면 구조를 따른다 |
| 하지 않을 것 | 프론트의 날짜 · 시점 · D-day 계산, 규칙 기반 조합 추천을 백엔드로 옮기기 — 백엔드에 같은 기능이 없다 |
| 실패로 볼 것 | 수당별 부분 제한(예 : "○○수당 미지급") 이 카드에서 "신청 불가" 로 뭉개진다 — `6502a06` 이 고친 오판이 되살아난 것 |
| 실패로 볼 것 | 한 카드에 판정이 두 개 보이거나, 카드 · 상세 · 에이전트 설명이 서로 다른 판정을 말한다 (명세 8장) |
| 실패로 볼 것 | AI 가 실패하거나 꺼져 있을 때 보드 · 담기 · 저장이 멈춘다 (명세 T21) |

## 5. 접근 방식

### 5.1 중복수혜 판정

| 방식 | 내용 | 얻는 것 | 내주는 것 | 선택 |
|---|---|---|---|---|
| **백엔드 결과 그대로 옮기기** | 서버가 `evaluateRules` 결과(상태 · 사유 · 제한 항목 · 질문 · 근거) 를 카드에 옮긴다 | 부분 제한 · 질문 · 기간 조건이 그대로 산다. 판정이 하나 | 결과를 카드 형식으로 바꾸는 변환 코드 | **채택** |
| 규칙을 프론트 형식으로 변환 | 백엔드 규칙을 프론트 `Restriction` 으로 바꿔 `restrictionBetween` 이 계산 | 프론트 코드 흐름 유지 | 프론트 판정은 막힘 · 불확실 2가지뿐이라 부분 제한 · 질문이 사라진다 | 제외 — 실패 조건에 걸림 |
| 나란히 보여 주기 | 백엔드 판정을 배지로 덧붙임 | 코드 변경 최소 | 한 카드에 판정 두 개 | 제외 — 실패 조건에 걸림 |

### 5.2 AI 계획

| 방식 | 내용 | 선택 |
|---|---|---|
| **에이전트 패널에서 부르기** | "나에게 맞는 경로 추천해줘" → `/api/plan` → 보드의 "AI 추천 경로 보기" 에 표시, 실패하면 규칙 추천으로 대체 (명세 8.2) | **채택** |
| 따로 버튼 · 창 | 보드 위에 새 버튼 · 결과 창 | 제외 — 추천 표시가 두 군데로 갈라짐 |

### 6.3 실제 수혜 충돌 → 백엔드

- `catalog.ts` 의 `baseEvaluator` 가 받는 `judgePolicy` 결과에서 `axes.restriction.current_restrictions` 를 읽어 카드 사유로 옮긴다.
- `evaluate.ts` 의 `applyConflicts` 에서 `participating` 기반 비교는 **실데이터일 때 건너뛴다.** 시연 가상 데이터일 때만 남긴다.

| 백엔드 결과 | 카드 판정 | 카드 사유 (`Reason`) |
|---|---|---|
| `applies` + `blocksParticipation` = true (전체 차단) | `blocked` | `PARTICIPATION_CONFLICT` · "현재 수혜 중인 ○○과 중복 불가" · 근거 문구 |
| `applies` + 부분 제한(`restricted_item` 있음 또는 차감 · 미지급) | 원래 판정 유지 (막지 않음) | `PARTIAL_RESTRICTION` · "○○수당 미지급" 같은 백엔드 `reason` |
| `needs_info` | 제한 항목(`restricted_item`) 이 없으면 `needs_check`, 있으면 판정 유지 — 백엔드 `judgePolicy` 와 같은 기준 (막힘이면 유지) | `RESTRICTION_QUESTION` · 백엔드 `question` |
| `not_applies` | 영향 없음 | 없음 |

- 근거 : 백엔드 `evidence`(공고 문구 · 주소 · 확인일) 를 카드 `evidence` 에 넣는다.

### 6.3.1 카드 판정 = 백엔드 자격 판정 (4장 결정)

지금 `catalog.ts` 는 "백엔드가 조건 충족 **그리고** 그 회차 조건을 사람이 모두 확인" 일 때만 신청 가능으로 본다. 그래서 실데이터 카드가 0장 초록이다 (6.6.1). 이것을 백엔드 판정 값 그대로 옮긴다.

| 백엔드 `personal` | 백엔드 뜻 | 카드 판정 | 카드 사유 · 배지 | 명세와의 관계 |
|---|---|---|---|---|
| `eligible` | 사람이 조사한 검증 정책이고 조건이 맞음 | **신청 가능** | 검증 배지 = 백엔드 `verifyLabel` (예 : "근거 확인 대기", "근거 확인됨") | 명세 6.1 "판정 · 선택 · 추천을 따로 갖는다" — 검토 상태를 판정에 섞지 않고 배지로 분리 |
| `code_met_unreviewed` | 공공 API 코드 조건만 맞음 (검증 정책 아님) | 확인 필요 | "일부 조건 충족 · 공고 확인 필요" | 명세 6장 161줄이 이 값에 정한 문구 그대로 |
| `needs_check` | 확인할 조건이 남음 | 확인 필요 | 백엔드 사유 그대로 | 같음 |
| `ineligible` | 조건 불충족 · 전체 차단 | 불가 | 백엔드 사유 그대로 | 같음 |

- 기간 · 모집 판정(마감, 접수 불교차, 예산 소진 등) 은 지금 새 화면 계산을 그대로 둔다. 일 단위 시점은 백엔드에 없다.
- 규칙 추천은 지금처럼 "신청 가능" 카드만 고른다. 명세의 "확인 필요 후보는 추천 제외" 의도는 그대로다.
- 내 기한 종류(`deadlineKind`) 의 "미검토면 기한 미정" 규칙은 그대로 둔다 (날짜 신뢰도 문제라 판정과 별개).
- PERSONA_A(11-22 기준) 로 백엔드는 1건이 `eligible` 이다 (청년 자격증 응시료 지원(인천)). 시연에 초록 카드가 적으면 6.1.1 대로 시연 인물을 조정한다.

### 6.4 담은 정책끼리 충돌 → 백엔드

- 카드마다, 그 카드를 뺀 나머지 담은 정책을 예정 수혜로 바꾼다.
	- `{ policyId, status: "planned", plannedStart: 담은 시점의 신청 시작일 }`
- 그 카드 정책의 승인 규칙과 함께 `evaluateRules(rules, benefits, plannedBenefits, now)` 를 부른다.
- 결과의 `planned_conflicts` 를 6.3 표와 같은 방식으로 옮긴다.
	- 전체 차단은 `DRAFT_CONFLICT`, `blocked`, `conflicts` 에 상대 offering 추가.
	- 기존 규칙대로 `canReplace` 를 계산해 비교 · 교체 화면을 그대로 쓴다.
- 규칙 기반 조합 추천(`recommended`) 도 같은 함수로 충돌을 검사한다.
- 백엔드 규칙은 정책 단위다. 같은 정책의 다른 회차끼리는 규칙이 없으면 제한하지 않는다 (명세 6장과 같음).

### 6.5 정보 필요 질문 → 에이전트 패널

- `Evaluation` 에 `questions: { policyId, ruleId, question }[]` 를 추가한다.
- 에이전트 패널은 질문이 있으면 먼저 보여 준다. 답은 정해진 선택지(예 / 아니오 / 날짜) 로 받는다.
- 답은 `benefits` 의 해당 값(마지막 지급일 · 상태 등) 을 고치고 다시 판정한다. 자유 입력은 외부 AI 로 보내지 않는다.
- **"아니오, 안 받아요" 답 (Claude 판단 · 송하우 확인 필요)** : `Benefit.status` 에는 "받은 적 없음"이 없다. 백엔드 `condition()` 을 읽어 보면 `eligible_unpaid`(자격만 있고 미수급) 는 `receiving` · `selected` · `within_months_after_end` 세 조건에서 모두 "해당 없음"이 된다. 그래서 "안 받아요" 답은 `{ policyId, status: "eligible_unpaid" }` 로 저장한다. 백엔드 판정 코드를 우회하지 않고 같은 함수가 판정한다. 뜻이 정확히 같지는 않으므로, 백엔드에 "받은 적 없음" 상태를 추가하는 쪽이 낫다면 송하우와 정한다.
- 답할 수 있는 질문 종류는 규칙의 `condition_type` 으로 정한다 : `receiving` → 받는 중 / 안 받음, `selected` → 선정됨 / 아님, `within_months_after_end` → 받는 중 / 끝남(마지막 지급일) / 안 받음. 그 밖의 질문은 10장대로 "기관 확인 필요" 사유로만 표시한다.

## 10. Claude 판단으로 정한 것 (검토 질문에서 나옴)

| 질문 | 정한 것 | 이유 |
|---|---|---|
| 담은 정책끼리 충돌(6.4) 에서 예정 수혜 기간은? | **그 카드의 이 시점 신청 구간(`stageWindow`) 을 수혜 기간으로 쓴다.** 시작 · 끝 둘 다 넘기고, 카드 자신도 대상(target) 예정 수혜로 넣는다. 끝이 없으면(상시) 공고 마감, 그것도 없으면 "확인 필요" | `evaluateRules` 는 원인 · 대상 양쪽 기간 4개가 있어야 "적용"을 낸다. 시작일만 넘기면 I4 가 늘 확인 필요가 되고 비교 · 교체가 켜지지 않는다. 실제 수혜 기간은 데이터에 없어 신청 구간이 가장 가까운 대용이다 — 거짓 충돌이 생길 수 있어 사유에 "예정 기간 기준" 을 붙인다 |
| 어떤 질문을 사용자에게 보여 주나? (6.5) | **답이 `Benefit` 칸(상태 · 마지막 지급일 · 예정 시작 · 끝) 에 담기는 질문만 묻는다.** 데이터 검수용 질문("이번 회차의 제한이 확인됐나요?" 등, 규칙 판정이 `blocked` 아닌 것) 과 담을 칸이 없는 질문(예외 조건, 활동 · 사업 유형, 월 지급액) 은 묻지 않고 카드에 "기관 확인 필요" 로만 표시 | 답해도 판정이 안 바뀌는 질문을 물으면 같은 질문이 끝없이 돈다 |

| AI 추천은 보드의 어느 카드에 붙이나? 저장되는 추천은? | AI 가 고른 `policyId` 를 정거장 월과 같은 달에 시작하는 시점의 카드에 붙인다. 그 시점에 없으면 같은 정책의 가장 이른 가능 시점 카드. 그 카드가 `blocked` 면 붙이지 않고 "AI 추천이 지금 일정과 맞지 않아요" 로 알린다. "추천을 새 계획으로 저장" 은 **보고 있는 추천**(AI 또는 규칙) 을 저장하고 출처를 남긴다 | AI 는 월 단위, 화면은 일 단위라 정확히 맞출 수 없다. 판정은 서버 카드 값이 우선(명세 8.2) |
