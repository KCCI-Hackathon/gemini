# 갈림길 백엔드 작업 계획

2026-11-19 · 백엔드 담당 실행 노트 · SQLite 구축 확정 · 11월 23일 정오 제출 기준

**온통청년 JSON은 원본 그대로 SQLite에 적재한다.** 프론트엔드는 날짜 표기, 코드의 한글 라벨, 빈 값 표시를 맡는다. 서버는 기존 정규화·판정 코드를 사용해 프론트와 AI에 같은 판정 결과를 제공한다. 첫 산출물은 대표 정책의 원본·공고 근거·API 응답·화면 표시 예시다.

## 1. 출발점과 착수 조건

11월 16일자 저장 스냅샷을 직접 집계했다. 4,020행의 정책번호는 모두 고유하다. 현재 코드가 상시로 매핑하는 원본 코드가 1,114건, 기간 지정 1,953건, 마감 953건이다. 참여 제한·추가 자격 두 필드에 ‘중복’이 들어간 정책은 58건이다. 이 수치는 **조사 후보를 찾는 기준선**이다. 상시 수혜 확정 건수나 중복 제한 전체 건수를 뜻하지 않는다. [수집기](../../scripts/fetch-snapshot.ts) · [정규화 규칙](../../lib/data/normalize.ts)

| 코딩 전에 결정할 것 | 확인 방법 | 결정 전 가능한 일 |
|---|---|---|
| ‘상시 수혜’가 연중 신청, 선정 후 계속 지급, 반복 신청 중 무엇인지 | 프론트 담당자와 카드 문구를 정하고 각 의미에 해당하는 공고 한 건씩 대조 | 세 개념을 분리한 필드 사전 작성 |
| 우선 검토할 정책·회차와 판정 승인 담당 | 시연 동선에 등장하는 정책부터 고르고 AI 담당자와 공식 URL·원문 인용·회차·확인일 전달 형식 합의 | 기존 검증 정책 6건과 후보 목록에서 표본 선정 |

설계 의견에는 **근거 한 건과 반례 한 건**을 붙인다. 예를 들어 ‘상시 코드면 지금 신청 가능’이라는 의견은 예산 소진 공고에 적용해 본 뒤 결정한다. 확인되지 않은 가정은 해당 필드와 판정의 구현을 보류하고 독립적인 작업부터 진행한다.

## 2. 원본 적재와 공고 조사

1. **온통청년 원본 보존 및 대조.** 정책번호를 문자열 키로 사용하고 각 레코드를 JSON 그대로 저장한다. 빈 문자열, 누락 필드, 코드와 날짜 원문을 보존한다. 적재 시 JSON 구조·총건수·정책번호 누락과 중복을 검사하고, 재추출한 레코드를 원본과 비교한다. 새 신청기간 코드처럼 해석이 필요한 값은 판정 단계에서 확인한다.
2. **중복수혜 제한 조사.** 참여 제한·추가 자격 외에도 지원 내용과 공식 공고에서 ‘동시 참여’, ‘유사사업’, ‘기수혜’, ‘재참여’, ‘중복 가능’ 등의 표현을 찾는다. 키워드가 없는 대표 공고도 직접 읽어 누락을 점검한다. 후보마다 기준 정책·회차, 제한 대상 사업명 또는 사업군, 제한 기간, 대상자 범위, 예외, 공식 URL·원문 인용·확인일을 남긴다. 동시 참여 제한과 과거 수혜자 제외를 구분하고 A 공고의 조건을 B 공고에도 자동 적용하지 않는다. 대상 사업을 정책번호에 연결할 수 없으면 원문 이름을 보존한다. 담당자가 근거를 승인한 회차만 판정에 반영하고 불명확한 건은 ‘확인 필요’로 전달한다.
3. **상시 정책 조사.** 상시 코드 1,114건을 1차 목록으로 만들고 기간형·결측 자료에서도 연중 접수 문구를 찾아 대조한다. 신청 방식, 기준일의 접수 상태, 선정 후 지급 기간·반복 가능 여부를 별도로 기록한다. ‘연중 접수하되 예산 소진 시 종료’라면 신청 방식은 상시, 소진 여부가 확인되지 않으면 카드에 조건을 표시한다. 사업 종료·모집 중단 공고와 회차 변경도 확인한다.
4. **결과 인계.** 전체에 대해서는 품질 통계와 후보 목록을, 대표 정책에는 검토 완료 근거표를 제공한다. 발견·검토·승인·미확인 건수를 분리해 프론트와 AI 담당자가 표시 범위를 알 수 있게 한다.

## 3. DB 구축

**11월 19일 결정: 11월 23일 제출본은 SQLite에서 적재·검토하고 승인된 데이터 버전을 JSON으로 고정해 배포한다.** 백엔드 담당자가 SQLite를 관리하고, 서비스는 배포물에 포함된 정책 스냅샷과 검증 근거를 읽는다. 고정 이후 수정한 내용은 다음 승인본을 내보내고 배포할 때 사용자에게 반영된다.

| 저장 단위 | 식별 및 보존할 내용 |
|---|---|
| 수집본과 정책 원본 | 수집본 ID·기준일·파일 해시, 수집본 안에서 고유한 정책번호, 원본 레코드와 수정일. 같은 자료 재적재 시 중복 생성 방지 |
| 공고 회차 | 정책번호·회차 ID로 검토 상태와 공식 공고에서 확인한 모집 기간을 연결한다. 검증한 값에는 해당 회차의 근거를 붙인다. |
| 근거와 조건 | 회차에 연결한 공식 URL·정확한 인용·확인일·승인 상태. 중복 제한과 상시 조건·예외가 각 근거를 참조하도록 외래키 설정 |

작업 순서는 스키마·제약조건 작성 → 대표 정책 적재 → 전체 스냅샷 적재 → 승인본 내보내기 → 기존 판정 결과와 대조다. 새 버전은 하나의 트랜잭션으로 적재하고 검증이 끝난 뒤 공개한다. 실패 시 이전 승인본을 다시 읽을 수 있어야 한다. 납품물은 재실행 가능한 적재 절차, 스키마, 백업에서 복원한 뒤 비교한 건수·판정 결과다. 개인 프로필이나 채팅 저장은 이번 DB의 용도에서 제외한다.

## 4. API 설계 및 팀 인계

### SQLite에 포함할 기존 데이터와 신규 규칙

- **기존 데이터**는 온통청년 원본(기준일과 정책 필드 전체), 검증 정책(기존 조건·회차·인용·출처·승인 상태·정책 관계), 검증 후보와 에이전트 검증 결과, 지역 코드, 로드맵 연결 관계까지 보존한다. 검증 평가 정답과 재현용 도구 호출 자료도 용도를 구분해 적재한다. 앱의 정규화된 `Policy` 구조는 원본에서 재현해 기존 로더 결과와 대조한다.
- **신규 규칙**은 `policy_overlap_rule`에 규칙 ID, 원인 정책 A, 영향받는 정책 B, 적용 회차, 제한 효과, 적용 조건·기준 시점·조건값, 예외, 근거 참조, 검토 상태를 담는다. 기존 `confirmedRelations`와 겹치는 관계는 원래 인용을 연결한다. 종료 후 대기기간과 수당 택일처럼 효과가 다른 조항을 구분하고, 같은 두 정책의 여러 조건도 보존한다.
- **이관 완료 기준**은 자료 종류별 레코드 수와 정책번호 대조, 필드 누락·빈 값·배열·인용문의 왕복 비교, 승인본으로 재생성한 판정 예시의 일치다.

### 채팅에서 받은 현재 수혜 내역

사용자가 채팅에 “지금 구직급여를 받고 있어요”라고 입력하면 에이전트가 정책 후보를 찾고, 정책명이 명확하면 즉시 반영하고 사용자가 수정할 수 있는 정책번호와 수급 상태를 판정 세션의 실제 수혜 내역에 반영한다. 동명이거나 지역·회차가 불명확하면 후보를 보여주고, 제한 판정에 필요한 날짜만 추가로 묻는다. “신청했어요”, “받고 싶어요”, “예전에 받았어요”는 각각 신청·계획·종료 상태로 구분한다.

백엔드는 실제 수혜 내역과 예정된 수혜 일정을 같은 승인 규칙에 각각 대조해 현재 제한과 계획 충돌을 따로 반환한다. 수혜 내역은 우선 사용자 세션 범위로 두고 정책 배포용 SQLite 백업에는 공공 데이터와 규칙만 포함한다. 실제 사용자 자유 입력을 외부 모델로 보내는 문제는 기존 AI 설계의 별도 결정 사항이다. 현행 전송 제한을 유지할 때는 서비스 내부에서 정책명 후보를 찾아 확인한 값으로 처리한다.

| 소비자 | 계약 초안 | 팀에 전달할 내용 |
|---|---|---|
| 프론트엔드 | 기존 `POST /api/judge`의 프로필·계획·답변 입력과 로드맵 응답을 유지한다. 카드에 필요한 신청 방식, 접수 상태, 중복 제한 결과·사유, 기준일과 근거 참조를 필요한 만큼 추가한다. | 상시·조건부·마감·근거 부족 각각의 요청/응답 JSON, 누락 필드의 기본 표시, 잘못된 입력의 오류 예시 |
| 프론트 상세 화면 | 목록에서 필요하지 않은 긴 인용은 상세 클릭 시 읽도록 협의한다. 별도 조회가 필요할 때만 정책번호·회차 기반 상세 API를 추가한다. | 정책 없음과 정책은 있지만 승인 근거가 없음을 구별하는 응답, 회차 선택 기준 |
| AI 담당자 | 검증 담당자가 정책번호·회차별 근거 후보를 전달하면 백엔드가 검토·적재한다. 계획 AI에는 서버 판정 결과와 승인 근거를 제공한다. | 같은 대표 정책의 입력·출력 파일, 근거 수정 시 새 버전 반영 절차. 기존 검증·계획 API의 모델 연동은 AI 담당 |

프론트와 AI 담당자가 **동일한 예시의 의미에 합의한 뒤** 계약을 고정한다. 특히 ‘제한 자료 없음’, ‘참여 여부 미입력’, ‘승인된 제한 조건 해당’을 구분한다. 선택 정보가 없는 사용자를 자동 탈락시키거나 근거 없는 중복 허용을 표시하면 인계 실패다.

### 팀원 교차 확인과 승인

백엔드 담당자가 규칙 한 건을 작성하고 다른 팀원 한 명이 B의 API 원문을 독립적으로 읽는다. 먼저 시연에서 실제 사용할 규칙부터 검토한다. 조사 후보는 정책번호 쌍 단위, 승인은 효과·시점·예외를 갖춘 규칙 단위로 집계한다.

| 검토 카드에 적을 것 | 예시 · 검토 전 |
|---|---|
| A → B / 근거 위치 | 구직급여 → 미래내일 일경험 사업 / B 정책번호 20250123005400110394의 ptcpPrpTrgtCn |
| 원문과 검토 질문 | “실업급여 수급자는 수급기간동안 일경험에 참여시 미래내일일경험사업의 청년지원금을 받을 수 없습니다. 단, 프로젝트형 일경험의 팀 단위 지원금은 사용할 수 있습니다.” 무엇이 제한되며 예외는 무엇인가? |
| 적용 예시 / 반례 | 현재 구직급여 수급 중 → 개인 청년지원금 제한 / 같은 사용자의 프로젝트형 팀 지원금 → 이 조항으로 차단하지 않음 |
| 결정 기록 | 작성자 / 다른 검토자 / 검토일 / 승인·수정 요청·보류 / 사유 한 줄 |

검토자는 ① A·B가 서로 다른 사업이고 해당 회차에 적용되는지 ② 원문의 방향·기준일·예외가 규칙과 일치하는지 ③ 적용 예시와 반례의 화면 결과에 동의하는지 확인한다. 모두 확인되면 승인한다. 근거는 분명하지만 규칙을 잘못 옮겼으면 수정 요청 후 재검토한다. 동일 사업의 지역 안내 가능성, 누락된 근거, 의견 불일치는 보류하고 필요한 증거 한 가지를 적는다. 승인한 원문이나 규칙 내용이 바뀌면 다시 검토한다.

### 확정한 사용자 흐름

- 채팅에서 정책과 상태가 명확하면 즉시 반영하고 ‘구직급여 · 수급 중 [수정]’처럼 표시한다. 모호한 경우에만 질문한다. 같은 건을 정정하면 기존 상태를 교체하고 현재 판정과 계획 충돌을 다시 계산한다.
- 충돌하는 정책도 대안으로 계획에 담을 수 있다. 같은 기간에 실제로 양립할 수 없는 조합을 확정할 때 하나를 선택하거나 일정을 변경한다. 수당 택일·차감이면 해당 수당 또는 금액에만 효과를 적용한다.
- 답변 정정 직후 카드를 갱신하고 이전 AI 설명을 숨긴다. 사용자가 ‘계획 다시 정리’를 누르면 갱신된 결과로 설명한다. 캐시 재사용은 기존 키 조건에 더해 최종 판정 결과와 승인 데이터 버전이 모두 일치할 때만 허용한다. 이전 요청의 늦은 응답도 새 설명으로 표시하지 않는다.

**검증은 정상 응답 한 건으로 끝내지 않는다.**

- 수집 중 마지막 페이지 실패, 총건수는 맞지만 ID 중복, 미등록 코드·비정상 날짜를 넣어 부분 자료 공개나 잘못된 ‘접수 중’ 표시가 없는지 확인한다.
- 같은 자료 두 번 적재, 수정 공고 재적재, 중간 실패 후 재실행, 이전 버전 복원에서 정책·회차·근거가 보존되는지 비교한다.
- 고정한 SQLite 백업을 새 작업 경로에서 복원하고 같은 승인 버전을 다시 내보낸다. 파일별 해시와 건수가 제출본과 일치하고, 그 JSON만 포함한 앱에서 대표 정책의 판정과 인용 근거가 재현되어야 한다.
- 중복 허용 예외, A→B 단방향 제한, 과거 수혜와 현재 참여, 시민이 ‘모름’을 선택한 경우를 공고 인용과 수동 대조한다.
- 상시 접수·예산 소진, 사업 종료, 한국시간 마감일 당일과 다음 날, 회차 전환 사례에서 DB·API·화면의 표시가 일치하는지 확인한다.
- 기존 테스트 전체와 빌드에 더해 프론트 담당자와 실제 카드 → 상세 근거, AI 담당자와 같은 회차 → 최종 설명을 각각 확인한다. 결과에 데이터 버전·재현 입력·기대값·실제값을 기록한다.

반복 실수와 판단 근거는 [백엔드 학습 노트](./backend-lessons.md)에 남긴다. 같은 원인의 사례는 기존 항목에 회귀 테스트나 근거만 추가한다.
