# 중복수혜 판정 에이전트 설계 기획서

2026-11-19 · AI 에이전트 담당 · **설계 확정(2026-11-19), 사용자 결정 반영(2026-11-20)** · 구현 전 · 관련: [중복수혜 노트](./2026-11-19-demo-overlap.md), [SQLite 실행 계획](./2026-11-19-sqlite-build-plan.md), [SQLite·서버 계획](./2026-11-19-sqlite-server-plan.md)

**요약.** 시연 3지역(포항시 남구, 인천 연수구, 경기 수원시)의 정책 원문을 Gemini 무료 API의 `gemini-3.5-flash`가 읽는다. AI는 "정책 A를 받고 있으면 정책 B를 받을 수 없다"는 문장을 찾아 A–B 쌍으로 만든다. 그다음 다른 역할의 호출로 스스로 다시 검증한다. 코드는 인용문이 원문에 그대로 있는지, A가 실제 정책번호로 연결되는지, 두 번 돌려도 같은지를 검사한다.

검사를 모두 통과한 규칙만 확정이다. 확정 규칙은 B 전체가 막히면 **수혜 불가**, 조사본에서 일부 항목 제한을 확정했으면 "수급기간 중 훈련장려금 미지급"처럼 막히는 항목으로 표시한다. 에이전트가 찾은 일부 제한을 포함해 나머지는 **확인 필요**다. 운영자 검증은 하지 않는다.

## 1. 왜 만드는가

- 프론트엔드에 "이 정책을 받고 있으면 저 정책은 받을 수 없다"를 정책 쌍으로 보여 주기 위해서다.
- 정책 원문에는 중복수혜 제한이 문장으로만 있고, 어떤 정책과 얽혀 있는지는 데이터에 없다.
- 전체 4,020건을 대상으로 하면 비용이 너무 크고 사실상 불가능하므로, 시연 3지역으로 범위를 좁힌다.
- 지금까지는 사람이 Claude 세션으로 조사했다(57쌍). 이제는 이 일을 에이전트에게 맡긴다.

## 3. 목표 · 비목표 · 실패 조건

**목표**
- 3지역 1,127건 안에서 A–B 중복수혜 쌍을 찾아 DB에 저장한다.
- 쌍마다 B 원문 인용, 근거 필드, 제한 효과, 조건(수급 중·종료 후 기간 등), 예외를 채운다.
- 정답 사례(57쌍과 표 3을 "쌍 + 조건 + 기대 효과"로 옮긴 것)에 대한 재현율과 확정 오판 수, 자가 검증의 신뢰도를 보고한다(9장).

**비목표**
- 3지역 밖의 정책
- 공식 공고 웹페이지 열기. 온통청년 API 원문만 읽는다
- 실행 중(사용자 요청마다) AI 호출. 미리 한 번 돌려 결과를 저장한다
- 사용자별 판정. 쌍을 저장하는 데까지가 이 에이전트의 일이고, 사용자 상태와의 대조는 기존 판정 코드가 맡는다

**실패 조건** — 동작하더라도 아래 중 하나라도 해당하면 실패다.
- "중복 가능"이라고 적힌 조항이 제한으로 나오거나, "차액 지원"·"차감"·"일부 항목 미지급" 같은 일부 제한이 B 전체의 **수혜 불가**로 나온다. 표 3에도 일부 제한이 섞여 있다(예: 실업급여 수급기간 중 훈련장려금 미지급). 그러므로 "제한 아님"이 아니라 **기대 효과**로 채점한다(9장)
- 원문에 없는 문장이 인용으로 저장된다
- A를 지어내거나 엉뚱한 정책번호에 연결한다
- 사용자의 수혜 여부를 모르는데 자동으로 탈락시킨다(쌍이 있어도 사용자 상태가 "모름"이면 확인 필요)
- 사용자 정보가 Gemini로 간다. 보내는 것은 공개 정책 원문뿐이다

## 4. 확인한 사실 (2026-11-19)

| 사실 | 설계에 주는 영향 |
|---|---|
| 3지역 1,127건. 비어 있지 않은 필드: `ptcpPrpTrgtCn` 246건(2.3만 자), `addAplyQlfcCndCn` 447건(4.3만 자), `plcySprtCn` 1,127건(16.1만 자) | 세 필드를 모두 보내면 약 22.8만 자 |
| 57쌍의 근거 필드: `ptcpPrpTrgtCn` 약 47쌍, `addAplyQlfcCndCn` 7쌍, `plcySprtCn` 1쌍. A와 B 모두 3지역 1,127건 안에 있다 | 세 필드를 다 읽어야 57쌍을 모두 찾을 수 있다 |
| **줄 단위 키워드 필터를 쓰면 57쌍 중 21쌍을 놓친다.** "제외 대상" 같은 제한어는 제목 줄에 있고 사업명은 그 아래 항목 줄에 있어서다(예: `국가근로장학생 / 해외파견자 …`, `(중앙부처) 고용노동부 청년내일채움공제 …`) | 줄을 잘라 보내지 않고 **필드 전체**를 보낸다 |
| `plcySprtCn`에서 제한어(중복·유사·제외·불가·차감·수급·수 없 등)가 하나라도 있는 레코드는 93건, 2.8만 자 | `plcySprtCn`은 레코드 단위로 걸러서 이 93건만 보낸다. 나머지 두 필드는 비어 있지 않은 레코드를 모두 보낸다 → 총 약 9.4만 자 |
| Gemini 무료 한도는 공식 문서에 숫자가 없고, AI Studio의 프로젝트 화면에서만 확인할 수 있다. 포럼(비공식)에는 2026년 9월 Flash 무료가 하루 20회라는 보고가 있다. Google 직원은 무료 등급이 "best effort"라고 했다 [^limits] | 하루 20회라도 며칠에 나눠 끝낼 수 있게 한다. 한도에 걸리면 간격을 두고 다시 시도하고, 받은 응답은 저장해 이어 간다(8장) |
| 무료 등급에서 보낸 내용과 응답은 Google 제품 개선에 쓰일 수 있고 사람이 검토할 수 있다 [^terms] | 공개 정책 원문만 보낸다. 사용자 정보는 보내지 않는다 |
| 기존 검증 에이전트(`lib/verify`)는 인용이 원문에 있는지 코드로 대조하고(`normalizeSpace`), 재현 자료를 저장해 API 키 없이 다시 실행한다(`scripts/verify-replay.ts`) | 같은 방식을 쓴다. 응답을 저장해 두면 다시 실행해도 무료 한도를 쓰지 않는다 |

| 사실 | 설계에 주는 영향 |
|---|---|
| 인용이 원문과 글자 그대로 일치: 1차 33/33, 2차 33/33. 형식 오류 0건 | 7장 ①은 거의 걸러낼 것이 없다. 그래도 검사는 남긴다 |
| 기대 효과 대조 8문구 중 7개가 두 번 모두 맞았다. 차감·차액·일부 부지급은 `partial`, "중복가능"은 `allowed`, 지원기간 설명은 `not_restriction`. 확정 오판(`blocks`)은 0건 | 제한·일부 제한·중복 가능을 가르는 핵심 판단은 Flash로 충분했다 |

| 정답 쌍 6개를 모두 `blocks`로 찾았다. 코드의 이름 비교로 3개가 정책번호에 연결됐다. 나머지 3개("경기도 청년 노동자 통장", "국가근로장학생", "청년내일저축계좌")는 AI 이름 연결이 맞는 정책번호를 골랐다. 청년내일저축계좌는 3지역에 레코드가 2개(`20260406005400212495`, `20260430005400113009`)이고, 57쌍에도 둘 다 A로 올라 있다 | 6장 ④의 AI 이름 연결 단계가 실제로 필요하다. 같은 이름의 레코드가 여럿이면 하나를 고르는 대신 묶음 전체를 연결한다(7장 ③에 따라 확인 필요) |
| 안정성: (B, 언급, `kind`)는 33개 중 27개가 같았고, 효과·조건·예외·제한 항목까지 모두 같은 것은 17개였다. 달라진 것은 대부분 `participation_block`↔`apply_block`, `condition_type`이 `receiving`↔없음이었다. 언급 표기도 "고용노동부 청년내일채움공제"↔"청년내일채움공제"처럼 흔들렸다 | ⑤를 엄격하게 적용하면 절반가량이 확인 필요가 된다. 효과 코드의 정의와 예시를 프롬프트에 더 분명히 넣고, 언급 비교 전에 부처·기관 접두어를 지운 뒤 다시 잰다 |
| 호출당 입력 약 5,700토큰, 출력 약 6,500토큰, 생각 토큰 약 4,000~5,000 | 분당 토큰 한도는 문제가 아니다. 묶음 크기를 정하는 것은 응답 시간이다(8장) |

**재시범(2026-11-19, 같은 9건, 보강한 프롬프트 + 자가 검증)**

보강 내용: 효과·조건 코드를 원문 동사·표현으로 고르게 하고, 부처·기관명을 사업명에서 떼어 `org`로 분리하고, 급여 수급 지위 조항을 포함하게 했다.

| 항목 | 1차 시범 | 재시범 |
|---|---|---|
| 인용이 원문과 글자 그대로 일치 | 33/33, 33/33 | 25/25, 36/36 |
| 기대 효과 대조(8문구 × 2회) | 14/16 (행복씨앗통장 2회 놓침) | **16/16** |
| 확정 오판(`blocks`) | 0 | 0 |
| 정답 쌍 6개 찾음 / 정책번호 연결 | 6/6, 6/6 | 6/6, 6/6 |
| 안정성: (B, 언급, `kind`) 일치 | 27/33 | **35/37** |
| 안정성: 효과·조건·예외·제한 항목까지 일치 | 17/33 | 26/37 |
| 자가 검증: 일부러 틀린 판정 3개 | — | **3/3을 `contradicted`로 잡음** |
| 자가 검증: 정답 쌍 판정 | — | 6/6 `supported` |
| 자가 검증: 실제 판정 중 `contradicted` | — | 1건: 행복씨앗통장 "유사 자산형성 지원사업" 제한에서 1차 추출이 예외("지원금을 받지 않고 해지")를 빠뜨렸다. 2차 추출에는 예외가 있었다. 검증 단계가 실제 누락을 잡았다 |
| 자가 검증 근거 인용이 원문 그대로 | — | 20/20 |

- 남은 불일치는 대부분 한 조항을 언급 하나씩 나눌지 묶을지의 차이다(1차 25조항, 2차 36조항). 언급 단위로 비교하면 대부분 같다.
- 효과·조건까지 완전히 일치한 것은 비교 가능한 35개 중 26개다. 어긋난 9개를 나누면 다음과 같다.
  - 4개: `allowed`·`not_restriction` 항목의 `condition_type` 차이. 화면에 영향이 없다.
  - 3개: 예외가 한 번은 있고 한 번은 없었다.
  - 2개: `partial` 항목의 `restricted_item`이 한 번은 비고 한 번은 채워졌다("훈련장려금", "월세지원금").
  - 화면에 영향이 있는 불일치는 5/35다. 그래서 7장 ⑤는 종류별로 필요한 항목만 비교하고, 프롬프트에서 `partial`이면 `restricted_item`을 반드시 쓰게 한다.
- **확정 기준을 알려진 쌍에 적용해 본 결과:** 교차 검토표 1~3번(구직급여·국민취업지원제도 → 청년도전지원사업, 재직청년 복지포인트 → 드림For 청년통장)은 확정이 된다. 4번(국가근로장학금 → 청년 노동자 통장)은 확인 필요가 된다. 사람이 교차 검토한 결과(1~3 승인, 4 보류)와 같다. 단, ⑥을 처음 쓴 대로 "같은 필드 전체"에 적용하면 3번도 확인 필요로 떨어진다. 같은 필드의 다른 항목 "중복사업 참여자 제한(상세내용 공고문 확인)"에 "공고문"이 있어서다. 그래서 ⑥은 조항이 속한 항목(가장 가까운 ○·□ 제목 줄과 그 줄)만 본다.
- 채점 도구 수정: "주거·교육급여는 신청 가능"이 "생계·의료급여는 제한"과 한 줄에 있어서, 처음 채점은 정상 판정을 오판으로 셌다. 언급한 사업 기준으로 고쳤다.

## 5. 접근 방식

| 방식 | 호출 수 | 판단 |
|---|---|---|
| **A. 코드 + AI 단계 분리** — AI는 문장 해석, 애매한 이름 연결, 자가 검증만 하고, 대상 선별·인용 대조·정책번호 연결·확정 판정은 코드가 한다 | 약 50회(추정, 8장) | **채택.** 무료 한도 안에서 며칠이면 돌아가고, 지어낸 인용이나 정책번호를 코드가 걸러낸다 |
| B. 모든 정책 쌍을 AI에 물어보기 | 1,127 × 1,126 ≈ 127만 쌍 | 불가능 |
| C. B 정책 하나당 1회씩, 3지역 정책 이름 목록(4.2만 자)을 함께 보내기 | 약 500회 이상 | 하루 20회 한도로는 한 달이 넘게 걸린다 |

## 6. 동작 흐름 (방식 A)

```
① 대상 선별(코드) → ② 조항 추출 ×2(AI) → ③ 인용 대조(코드) → ④ A 연결(코드 → 남은 것만 AI)
→ ⑤ 자가 검증(AI) → ⑥ 확정 판정(코드) → ⑦ 57쌍과 합치기(코드) → data/overlap/*.json → npm run db:build
```

1. **대상 선별 (코드).** 3지역 1,127건에서 `ptcpPrpTrgtCn`·`addAplyQlfcCndCn`이 비어 있지 않은 레코드는 전부, `plcySprtCn`은 제한어가 있는 93건만 고른다. 필드 단위로 묶고, 묶음 하나가 약 6,000자를 넘지 않게 나눈다(8장). 한 필드를 여러 묶음에 쪼개지는 않는다.
2. **조항 추출 (AI, 묶음당 독립 호출 2회).** 입력은 `{정책번호, 정책명, 필드명, 필드 전문}` 목록이다. AI는 중복·동시 수혜와 관련된 조항마다 아래 JSON을 낸다. JSON으로만 답하게 요청하고(`responseMimeType`), 형식은 코드가 검사한다. 효과·조건 코드는 원문의 동사·표현에 대응시킨 정의를 프롬프트에 넣는다(시범 프롬프트 기준).
   ```jsonc
   { "b_policy_id": "20250122005400110346", "field": "ptcpPrpTrgtCn",
     "quote": "구직급여를 받고 있거나",                 // 원문 그대로
     "mentions": [{ "text": "구직급여", "org": null, "type": "program" }],   // org: 앞에 붙은 부처·지자체명, type: program | category | law
     "kind": "blocks",        // blocks | partial | history | allowed | org_decides | not_restriction
     "effect_type": "participation_block", "condition_type": "receiving",
     "condition_params": {}, "exception": "수급자격만 있고 수급하지 않으면 참여 가능",
     "restricted_item": null,   // 일부 항목만 막히면 원문 표기(예: "청년지원금", "훈련장려금"), B 전체면 null. kind가 partial이면 반드시 채운다
     "period_text": null }      // 기간·연도·순서 조건 원문(예: "`24~`25년", "참여한 뒤"), 없으면 null
   ```
   `kind`가 `allowed`·`not_restriction`인 조항(표 3 유형)도 기록한다. 이 조항들은 쌍을 만들지 않고 평가에만 쓴다. `category`·`law` 언급은 정책번호에 연결하지 않는다. 대신 B 쪽에 "원문 제한 문구 있음, 확인 필요"로만 남는다. 기존 `restrictionAxis`의 `official_quote` 표시와 같다.
3. **인용 대조 (코드).** `quote`가 해당 레코드·필드 원문에 공백만 다르고 그대로 있는지 `normalizeSpace`로 확인한다. 없으면 그 조항을 버리고 실패 목록에 남긴다. 같은 묶음을 1회 다시 묻고, 그래도 없으면 버린다.
4. **A 연결.**
   - 코드가 먼저 `mentions.text`를 3지역 1,127건의 정책명과 맞춰 본다. 비교 전에 공백·괄호·연도 접두어(`2026년`)·기관 접두어(`(연수구)`)를 지운다. **이 정규화는 후보를 찾는 데만 쓴다.** 정규화하면 이름이 같아지는 묶음이 3지역에 129개나 있다(예: 인천시와 연수구가 같은 월세 지원을 각각 안내). 그래서 "한 건만 남았다"는 이유만으로 확정하지 않는다(7장 ③).
   - 정확히 한 건만 맞으면 연결한다. 연결 결과에는 이름이 같은 묶음의 다른 정책번호도 함께 남긴다.
   - 여러 건이 맞거나 하나도 안 맞으면, 문자열 유사도 상위 5건을 후보로 묶어 AI에 묻는다. 여러 언급을 한 번에 묶어 보낸다. AI의 답은 후보 정책번호 중 하나 또는 `none`만 허용한다.
   - 자기 자신(A=B)이나, 이름이 같은 전국·지역 안내끼리는 쌍으로 만들지 않는다.
5. **자가 검증 (AI, 약 40건당 1회).** [결정] 사람 대신 에이전트가 스스로 확인한다. 추출 단계와는 다른 역할의 프롬프트로, ②~④에서 만든 판정을 하나씩 B 원문과 대조한다.
   - 입력: B 필드 전문, 판정(A 언급, `kind`, `effect_type`, 조건, 예외, `restricted_item`), 인용
   - 출력: `verdict`(`supported` = 원문이 판정을 뒷받침 / `contradicted` = 원문과 어긋남 / `insufficient` = 원문만으로 판단 불가), 이유 한 줄, 근거 인용(원문 그대로)
   - 코드가 근거 인용이 원문에 있는지 다시 확인한다. `contradicted`는 판정을 버리고 기록만 남긴다. `insufficient`는 확인 필요로 둔다.
   - 한계: 추출과 같은 모델이라 같은 맹점을 공유할 수 있다. 그래서 일부러 틀리게 만든 판정을 섞어, 검증 단계가 틀린 판정을 잡아내는지 매번 잰다(9장).
6. **확정 판정 (코드).** 7장 기준.
7. **57쌍과 합치기 (코드).** 9장 기준. 결과를 `data/overlap/evidence.json`·`rules.json`에 쓰고 `npm run db:build`로 적재한다.

## 7. 수혜 불가 / 확인 필요 기준

아래 일곱 가지를 **모두** 만족해야 규칙이 **확정**(`blocked`)이다. 하나라도 빠지면 **확인 필요**(`needs_check`)이고, 빠진 항목이 화면의 사유가 된다. AI가 하는 일은 ②의 분류, 기간 문구 추출, ⑦의 검증 판단이다. 나머지는 코드가 검사한다.

| # | 조건 | 검사 주체 | 빠졌을 때의 확인 필요 사유(예) |
|---|---|---|---|
| ① | 인용이 B 원문 필드에 그대로 있다 | 코드 | (이 경우는 저장하지 않음) |
| ② | `kind = blocks`(동시 참여·수급 불가, 참여 제한, 선정 제외, 신청 불가) | AI 분류 | 일부 지원만 제한(`partial`), 과거 이력 제한(`history`), 기관이 판단(`org_decides`) |
| ③ | 언급이 사업 이름(`program`)이고, 정확한 이름 비교로 A가 한 건으로 연결됐고, 이름이 같아지는 묶음이 그 한 건뿐이며, 언급에 지역·기관명(예: "인천", "경기도")이 있으면 A의 주관·등록 기관과 맞다 | 코드 | 사업군 지목(`category`), 법 조항 추론(`law`), AI가 후보 중에서 고름, 같은 이름의 정책이 여러 기관에 있음 |
| ④ | A와 B의 신청 연도가 같거나, 한쪽이 상시 모집이다(`aplyYmd`·정책명의 연도) | 코드 | 회차가 다름(예: 2025년 청년애꿈 ↔ 2026년 사업) |
| ⑤ | **독립된 두 번의 호출**(저장본 재생은 표로 세지 않음)에서 같은 A–B·`kind`가 나오고, 종류별로 필요한 항목이 같다. `blocks`: `effect_type`, `condition_type`, `condition_params`, 예외 유무. `partial`: 여기에 `restricted_item`. 예외 문구의 표현 차이는 ⑦이 내용을 본다 | 코드 | AI 판단이 실행마다 달라짐(예: 한 번은 신청 제한, 한 번은 선정 제한) |
| ⑥ | [결정 2A] 기간 문구가 없거나, 기준 사건과 기간이 원문에 명시되고 구조화한 값이 일치한다(예: 지급 종료 후 6개월). `period_text`에는 원문을 보존한다. 가장 가까운 ○·□ 제목 줄과 인용 줄에 `별표`, `첨부`, `공고문`, `지침`, `상세내용`이 없어야 한다 | 코드 | 기준 사건·기간값 불명, 다른 연도·횟수·순서 조건이 남거나 외부 자료를 참조하는 경우 |
| ⑦ | 자가 검증(6장 5)의 `verdict`가 `supported`이고, 그 근거 인용이 원문에 있다 | AI 검증 + 코드 | 검증 단계가 원문만으로 판단할 수 없다고 봄(`insufficient`) |

- [결정] ③에서 AI가 고른 연결은 확인 필요로 둔다. 이름이 비슷한 다른 사업에 잘못 연결되는 위험이 가장 크기 때문이다. 시범의 정답 쌍 6개 중 3개가 AI 연결이었다("국가근로장학생"→국가근로장학금 등). 이 제안대로면 이런 쌍은 맞게 연결돼도 확인 필요로 남는다.
- ⑥은 API 원문만 읽는다는 범위(3장 비목표)를 지키기 위한 장치다. 공고문·별표를 읽지 않으므로, 그 내용에 기대는 조항은 확정하지 않는다.

**규칙 확정과 개인에게 적용하는 일은 따로 한다.**
- DB에는 규칙이 확정인지와 함께, **무엇이 막히는지**(`effect_type`, `restricted_item`)와 **어떤 사용자 사실이 필요한지**(`condition_type`, `condition_params`)를 따로 저장한다.
- 화면은 필요한 사용자 사실이 모두 채워졌을 때만 그 효과를 표시한다.
  - B 전체가 막히는 확정 규칙(`restricted_item = null`) → "수혜 불가"
  - [결정 1B] 에이전트가 찾은 `partial`은 항목을 적고 항상 확인 필요로 표시한다. 조사본에서 일부 항목 제한을 확정한 규칙은 개인 조건 충족 시 “수급기간 중 훈련장려금 미지급”처럼 해당 항목만 표시한다.
  - 사용자 사실이 없거나 "모름"이면 → 확인 필요 + 필요한 질문 하나
- [결정 3A] `/api/judge`의 `benefits[]`에서 실제 미수급(자격만 있음), 공고일 당시 신분, 해당 월 지급액을 선택적으로 받는다. 해당 사실이 필요한 규칙에만 사용하며 0원과 미입력을 구분한다. `Profile.participating`만으로 실제 수급·선정·지급일을 추정하지 않는다. 필드와 테스트는 [구현 계획 T13](./2026-11-19-overlap-agent-implementation-plan.md)에 적었다.

## 8. Gemini 호출 설계

- **실행 위치:** [제안] 로컬 스크립트 `scripts/overlap-agent.ts`. 배포된 서버는 Gemini를 부르지 않는다. 키는 `.env.local`의 `GEMINI_API_KEY`에 넣고 배포 환경에는 넣지 않는다(`YOUTH_POLICY_API_KEY`와 같은 방식). 모델 이름은 `GEMINI_MODEL`로 받는다(기존 `VERIFY_MODEL`과 같은 방식).
- **호출 방법:** 새 의존성 없이 `fetch`로 Gemini REST의 `POST /v1beta/models/gemini-3.5-flash:generateContent`를 부른다. 키는 `x-goog-api-key` 헤더로 보낸다. `generationConfig.responseMimeType = "application/json"`으로 JSON만 받는다. 시범에서 이 방식으로 형식 오류 0건이었다.
  - 응답 형식을 스키마로 강제하는 기능은 공식 문서가 새 Interactions API로 옮겨 가 있었다. 기존 방식의 필드는 확인하지 못해 쓰지 않는다.
  - 공식 문서에 최신 Flash는 temperature를 무시한다고 적혀 있다. 그래서 결과가 실행마다 다를 수 있다고 보고 ⑤로 잰다.
- **호출 시간(시범 실측, 2026-11-19):**
  - 1차 시범: 약 6,100자 묶음의 추출 1회가 약 1.5~2분, 이름 연결 17건이 75초였다.
  - 재시범(보강 프롬프트): 추출 169초(503 한 번 뒤 1분 쉬고 재시도), 152초, 이름 연결 19건 54초, 자가 검증 20건 203초였다. 4회 호출 전체가 약 10분 걸렸다.
- **[제안] 묶음 크기를 약 6,000자로 한다.** 시간 제한은 없앴지만, Node `fetch`는 응답 헤더를 5분까지만 기다린다. 6,000자 묶음의 응답에 이미 2.5~3.5분이 걸렸으므로, 원래 계획한 1.5만 자 묶음은 5분을 넘겨 매번 실패할 가능성이 크다(추정).
- **호출 예산(추정, 6,000자 묶음 기준):** 조항 추출 약 16묶음 × 2회(⑤ 안정성 확인) = 32회, 이름 연결 약 6회(시범 9건에서 17건 → 전체 약 250건으로 추정, 호출당 약 40건), 자가 검증 약 12회(시범 9건에서 판정 약 25건 → 전체 약 480건으로 추정, 호출당 약 40건). 합계 약 50회다. 이 중 원래 계획(1.5만 자 묶음)의 추정은 약 20~25회였다.
  - 사용자가 받은 Flash 무료 범위(2026-11-19, 2차 자료)는 RPM 5~15, RPD 20~250, TPM 25만~100만이다.
  - 하루 20회라면 사흘, 250회라면 하루에 끝난다.
  - 재시범 실측(호출당 약 1~3.5분, 평균 약 2.5분)으로 보면 약 50회 × 2.5분 ≈ **2~2.5시간**(추정). 503이 나면 1분부터 쉬었다가 다시 보내므로 더 길어진다.
  - 요청 하나는 약 6,000자(입력 약 5,700토큰)라서 분당 토큰 한도의 하한(25만)보다 훨씬 작다.
  - 사용자가 11/20 제공한 **Gemini 3.6 Flash** 표시값은 분당 요청 2/5, 분당 토큰 6.16K/250K, 일일 요청 17/20이다. 실행 모델 `gemini-3.5-flash`의 한도는 이 표로 확인할 수 없다.
- **시범 실행(완료, 결과는 4장):** 정책 9건으로 두 번 했다. 대상은 교차 검토표 4건이 들어 있는 B 정책 3개(청년도전지원사업, 드림For 청년통장, 청년 노동자 통장)와 표 3·행복씨앗통장의 "중복 가능·차감" 사례 6건이다.
- **한도 대응:** 요청 사이에 13초 이상 쉰다(분당 5회 이하). `429`도 아래 재시도 규칙을 따른다. 하루 한도를 다 쓴 경우라면 다음 날 한도가 풀릴 때까지 10분 간격으로 계속 시도한다.
- **혼잡 대응(2026-11-19 확인):** 시범 실행에서 `gemini-3.8-flash`·`3.7-flash`·`3.5-flash`가 모두 `503 UNAVAILABLE`("high demand")을 돌려준 적이 있다. 성공한 호출도 한 번에 1~3.5분 걸렸다. 그러므로 **11/23 직전에 처음 돌리면 안 된다.**
  - [결정] 모델은 `gemini-3.5-flash` 하나만 쓴다. 다른 모델로 넘어가지 않는다. 그래서 7장 ⑤의 두 번 추출은 항상 같은 모델이다.
  - [결정] 시간 제한 없이 **성공할 때까지** 다시 시도한다(2026-11-19). 처음에는 2분, 다음에는 4분 제한을 뒀지만, 4분 제한으로도 연속 실패해서 바꿨다.
    - 응답 없음·`503`·`429`·`500`이면 1→2→4→8→10분(최대) 쉬고 다시 보낸다. 시도마다 회차와 시각을 기록한다.
    - 키·요청 형식 오류(`400`·`403`·`404`)는 다시 보내도 같으므로 바로 멈춘다.
    - 한 번 시도의 대기는 Node `fetch` 기본값(응답 헤더 5분)까지다. 그 뒤에는 실패로 보고 위 간격으로 다시 보낸다.
    - 받은 응답은 바로 저장하므로, 중간에 멈춰도 다시 실행하면 실패한 호출부터 이어 간다.
    - 주의: 실패한 요청이 하루 한도에서 차감되는지는 확인하지 못했다. 차감된다면 재시도가 한도를 쓴다.
  - 참고(2026-11-19): 3.8·3.7은 시범 중 503이 잦았다. `2.5-flash`는 목록에는 보이지만 호출하면 404("no longer available to new users")였다.
  - 응답마다 모델 이름을 저장하고, 보고서에 표시한다.
- **응답 저장과 재현:** [제안] `data/overlap-agent/responses/<요청 해시>.json`에 원 응답을 저장하고 커밋한다. 같은 요청은 저장본을 쓰므로 다시 돌려도 한도를 쓰지 않는다. 결과에는 모델 이름과 실행일을 함께 남긴다.
  - 요청 해시에는 모델 이름과 **호출 순번(1차·2차)**을 넣는다. 그래서 7장 ⑤의 두 표는 항상 서로 다른 실제 호출에서 나온다. 저장본을 다시 읽는 것은 재현이지 두 번째 판단이 아니다.
  - 채점할 때는 지금 요청과 해시가 정확히 같은 저장본만 읽는다. 시범 실행에서 이전 프롬프트·다른 모델의 저장본이 섞일 뻔했다.
- **제출용 스냅샷 [결정 4-2 A·5A].** 11/20에 지정한 `D:\pathfinder\data\snapshot\current.json` (기준일 2026-11-16, 4,020건)을 사용한다. 원문이 바뀌면 해당 입력의 요청 해시를 다시 계산한다. 새 입력으로 재검증을 통과할 때까지 조사본만 제공한다. 정책이나 인용이 사라져 적재에 실패하면 이전 정상 배포본을 유지한다.

## 9. 57쌍과 합치기, 평가

**합치기 [제안]**
- 57쌍은 공식 자료와 대조한 기록(노트 표 1의 마지막 열)이 있으므로, 같은 A–B 쌍에서는 57쌍의 판정을 우선한다.
- 57쌍이 "확인 필요"이고 에이전트가 "수혜 불가"면 확인 필요로 둔다(더 신중한 쪽).
- 에이전트만 찾은 쌍은 7장 기준을 그대로 따른다.
- 57쌍의 판정은 노트 표 1의 마지막 열에 문장으로만 있다. 이를 `blocked`/`needs_check`와 효과·조건 값으로 옮기는 작업을 한 번 해서 `rules.json`에 넣는다. 이 열은 "참여 제한 ·", "선정 제한 ·"처럼 효과로 시작하는 문장과 "확인 필요"로 나뉘어 있다.
- 출처를 `source = research | agent`로 남긴다. 화면에는 구분해 표시하지 않는다(2장 결정).

**평가 (실행마다 보고서 `data/overlap-agent/report-<run_id>.md`)**
- **57쌍과 합치기 전에, 에이전트 단독 결과로** 채점한다.
- 채점 단위는 "정책 쌍"이 아니라 **정책 쌍 + 적용 조건 + 기대 효과**다. 예:
  - 구직급여 → 청년도전지원사업: "현재 수급 중"과 "지급 종료 후 6개월 미경과"는 각각 참여 제한이고, "수급자격만 있음"은 예외다(3건으로 채점)
  - 주거급여 → 청년월세: 차감(`partial`). Codex는 월차임분 금액에 따라 실제 결과가 갈린다고 지적했다(인천 월세 FAQ). 이 지적은 원문으로 아직 확인하지 않았다. 확인되면 금액별 사례를 따로 둔다
- 정답 사례 표 `data/overlap-agent/cases.json`: `{b, a?, mention?, phrase, condition?, expect_kind[], expect_effect?, expect_item?}`. 57쌍의 "직접 연결 제외"·"확인 필요" 행은 `expect`를 확인 필요로 둔다.
  - 판정은 언급한 사업 단위로 한다. 한 줄에 "생계·의료급여는 제한, 주거·교육급여는 가능"이 함께 있는 경우가 있다(재시범에서 채점 도구가 이를 오판으로 셌다가 고쳤다).
  - 이 표는 아직 시범용 14건(정답 쌍 6 + 효과 대조 8)뿐이다. 57쌍 전체와 표 3을 옮기는 작업은 구현 계획의 첫 과제다.
- 지표
  - 재현율: 정답 사례 중 기대 효과까지 맞힌 수
  - 확정 오판: 기대가 확인 필요나 일부 제한인 사례를 `blocked`로 낸 수. [결정] 통과 기준은 **0건**
  - 표 2(상대 레코드 없음): 정책번호가 아닌 `none`으로 끝나야 정상
  - 새로 찾은 쌍: 정답이 없으므로 [결정] 자가 검증(6장 5)으로 확인한다. 보고서에는 `supported`/`contradicted`/`insufficient` 수를 싣는다.
  - 자가 검증의 신뢰도: 실행마다 일부러 틀리게 만든 판정을 섞는다(예: 차감 조항을 `blocks`로, "중복가능" 항목을 `blocks`로, 수급자격만 있는 예외를 제한으로). 검증 단계가 이를 `contradicted`로 잡은 비율과, 정답 사례를 `supported`로 본 비율을 함께 보고한다. [결정] 틀린 판정을 하나라도 `supported`로 통과시키면 그 실행은 불합격이다.
- **통과해야 내보낸다.** `db:export`는 같은 `run_id`의 보고서가 통과일 때만 에이전트 출처 규칙을 내보낸다. 통과하지 못하면 `source = research`(57쌍)만 내보낸다

## 10. DB와 기존 계획에서 바뀌는 것

운영자 검증을 하지 않기로 했으므로 [SQLite 실행 계획](./2026-11-19-sqlite-build-plan.md)의 아래 항목을 고쳐야 한다. 이 기획서가 승인되면 함께 고친다.

| 기존 | 바뀔 내용 |
|---|---|
| `review_status`(draft/on_hold/approved…) + "승인이면 작성자 ≠ 검토자" CHECK | `judgement`(`blocked` = 수혜 불가 / `needs_check` = 확인 필요) + `needs_check_reason`, `source`(`research`/`agent`), `model`, `run_id`로 바꾼다. 사람 검토자 CHECK는 지운다 |
| 승인되고 회차(`target_round_id`)가 있는 규칙만 내보내기 | `blocked`·`needs_check`를 모두 내보낸다. 회차 대신 7장 ④의 연도 일치 검사를 쓴다. 회차가 기록된 정책은 6건뿐이어서다 |
| `kind`의 `allowed`·`not_restriction`, A를 연결하지 못한 조항 | 새 테이블 `agent_clause`에 보관한다(평가·추적용, 화면에는 내보내지 않음) |
| 규칙 열(`effect_type`, `condition_type`, `condition_params_json`, `exception_json`) | `restricted_item`, `period_text`, `verify_verdict`·`verify_quote`(자가 검증 결과), `a_group_ids`(이름이 같은 묶음의 다른 정책번호)를 더한다. `effect_type`·`condition_type`의 허용값은 시범 프롬프트의 정의와 같게 맞춘다 |
| 교차 검토표 4건(사람이 승인) | 57쌍에 포함되므로 `source = research`로 들어간다 |
