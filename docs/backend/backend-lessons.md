# 백엔드 학습 노트

반복되는 실수를 막기 위해 **관찰한 사실 → 다음 작업에서 확인할 것 → 근거 또는 회귀 테스트** 순서로 기록한다. 같은 원인의 사례는 한 항목에 합치고 검증 방법을 최신 상태로 유지한다.

| 주제 | 확인한 사실 | 다음 작업에 적용할 점 |
|---|---|---|
| 전체 수집 판정 | 기존 수집기는 수집한 행 수를 첫 페이지의 총건수와 비교한다. 일부 페이지가 반복되면 행 수만 맞을 수 있다. [수집기](../../scripts/fetch-snapshot.ts) | 총행 수와 고유 정책번호 수를 함께 확인하고, 페이지 중복 사례를 회귀 테스트에 넣는다. |
| 확인 안 된 전제로 결론 | (2026-11-19) ① `node_modules`가 없는데 `npx vitest`로 `node:sqlite` 동작을 시험해 npx가 임시 패키지를 받아 실행했다. 그래서 결과가 무효였다. ② Vercel 요금제 한도를 기억에 기대어 설명했다. ③ 실행 계획의 Windows 교체 위험을 "자기 연결" 문제로 추정해 썼다. 실제로 시험해 보니 다른 연결이 DB를 열고 있을 때 `renameSync`가 `EPERM`으로 실패했다. ④ Gemini 시범 실행이 `503`을 출력하자 "3.7·3.5 모두 실패"라고 보고했다. 실제로는 첫 호출이 성공해 저장돼 있었고 두 번째 호출만 실패했다. 오류에 어느 단계인지가 없었고, 저장된 파일도 보지 않았다. 같은 스크립트가 저장된 응답을 단계 이름과 모델만으로 골랐다. 그래서 이전 프롬프트의 응답이 채점에 섞일 수 있었다. ⑤ `sed` 수정 뒤 `grep -c` 결과가 2라는 숫자만 보고 "바뀌지 않았다"고 보고했다. 실제로는 수정이 됐고, 남은 2개는 주석이었다. ⑥ 중복수혜 계획 조사 때 존재하지 않는 `lib/agent/handler.ts`를 검색 경로에 넣어 `rg`가 종료 2를 냈다. `rg --files lib/agent`로 실제 파일 `run.ts`를 확인했다. 표 1 발췌 명령이 빈 출력이었을 때도 행별 번호와 원문을 다시 출력해 11~67행을 확인했다. ⑦ 모델 전환 계획에서 보고서를 삭제한 뒤 재생하도록 했지만 호출별 모델 선택을 복원할 입력을 지정하지 않았다. | 위험을 적기 전에 최소 재현을 실행하고, 그 결과를 계획에 적는다. 빈 상태 복원 절차에는 먼저 보존할 입력을 적고, 보고서를 삭제해도 같은 결과를 낼 수 있는지 점검한다(중복수혜 구현 계획 T5·T14). 실패를 보고하기 전에 저장된 결과와 실패한 단계를 확인한다. 여러 단계를 도는 스크립트의 오류 메시지에는 단계 이름을 넣는다. 저장본은 요청 전체(모델+프롬프트)의 해시로만 찾는다. 검색 경로는 `rg --files`로 확인하고 종료 코드와 실제 출력 행을 함께 본다. 시험 전에 `ls node_modules/.bin/<도구>`로 로컬 도구가 있는지 확인한다. 외부 서비스의 한도·요금은 공식 화면이나 문서로 확인한 뒤에만 쓰고, 확인 전에는 "미확인"으로 표시한다. 모르는 정보는 작업 전에 담당자에게 묻는다. |
| 채점 도구가 정답을 오판으로 셈 | (2026-11-19) 재시범 채점이 행복씨앗통장을 "오판(blocks)"으로 셌다. 원문 한 줄에 "생계·의료급여 수급자(주거·교육급여 수급자는 신청 가능)"가 함께 있었고, 모델은 생계·의료급여만 막고 주거·교육급여는 허용으로 제대로 나눴다. 채점이 인용 문자열만 보고 판단했다. 보고 전에 원 응답을 열어 보고 찾았다. | 채점은 문구가 아니라 **언급한 사업 단위**로 한다. 채점 규칙을 만들 때 제한과 허용이 한 줄에 함께 있는 사례를 넣는다. 오판으로 나오면 원 응답을 본 뒤에 보고한다. |
| 원본 왕복 비교 | `data/snapshot/current.json`은 Python 형식(`", "`, `": "`)이다. `JSON.stringify`로 다시 쓰면 내용이 같아도 바이트가 다르다(5,226,760 vs 5,009,692 bytes). | 왕복 비교는 파싱 후 `JSON.stringify`한 해시로 한다. 원본 파일 바이트 해시는 출처 식별용으로만 따로 보존한다. [실행 계획 Task 3 `canonical-hash`](./2026-11-19-sqlite-build-plan.md) |
| 상시 표시 | 기존 정규화는 신청기간 코드를 상시로 분류한다. 이 값이 설명하는 것은 신청 방식이다. [정규화](../../lib/data/normalize.ts) | 접수 가능 상태와 지급 기간은 별도 근거로 확인한다. 예산 소진 조건이 있는 공고를 검토 표본에 포함한다. |
| 불필요한 맥락으로 Codex 토큰 증가 | (2026-11-20) 긴 계획과 코드·테스트 출력을 반복해 읽고 전체 대화 맥락을 병렬 에이전트 3개에 전달했다. Gemini 실호출은 0회였다. | 실패한 작업과 필요한 파일·줄만 읽는다. 위임이 필요하면 역할과 입출력 계약만 전달한다. 통과한 테스트는 건수·종료 코드만 보고, 변경 후 확인이 필요한 경우에 다시 실행한다. |
| 재시도 사유 누락으로 실호출 지연 원인 확인 불가 | (2026-11-20) 응답 43건을 저장한 뒤 진행이 멈췄지만 기존 로그로는 일시 오류와 한도를 구분할 수 없었다. 로그를 보완해 같은 실행을 재개한 뒤 Gemini 3 Flash의 HTTP 429를 확인했다. | 재시도 시점에 모델·단계·HTTP 상태·다음 시각을 남긴다. 저장된 응답을 재사용하고, 429는 일일 한도의 구조화 근거가 있을 때만 확정한다. |
| Vercel 배포 환경과 검증 권한의 기본값 | (2026-11-21) 새 프로젝트의 첫 CLI 배포는 자동으로 Production에 배정됐다. 이후 환경을 지정해 Preview를 생성하고 서울 리전과 API 8건을 확인했다. 인증 확인 중 `vercel curl`이 자동화 우회 키를 만들었으며 검증 후 해당 키를 회수했다. | 새 프로젝트는 첫 배포 동작과 대상 환경을 실행 전에 확인한다. 환경을 명시하고 완료 출력으로 대조한다. 보호된 URL은 인증 도구가 지속 권한을 생성하는지 확인하고 기존에 승인된 인증으로 검증한다. |
| 빌드와 테스트 동시 실행 시 시간 초과 | (2026-11-21) 통합 빌드와 전체 테스트를 동시에 실행하자 테스트 3건이 5초 제한을 넘겼다. 빌드 완료 뒤 워커 2개로 다시 실행해 374건 모두 통과했다. | 같은 머신에서는 빌드와 전체 회귀 테스트를 순차 실행한다. 시간 초과가 발생하면 실패 원인을 먼저 확인하고, 단독 실행 결과로 판정한다. |
