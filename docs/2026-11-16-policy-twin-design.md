## 1. 무엇을, 왜 만드는가

**한 줄 정의** [합의, 확정]
갈림길은 취업·수료·창업 등 청년의 상황 변화에 따라 달라지는 정책 자격을 찾아주고, AI 에이전트가 공식 공고를 직접 탐색·검증해 그 변화의 이유와 다음 행동까지 안내하는 서비스다.

**구조**: 에이전트가 정책을 검증하는 서비스 옆에 갈림길 기능을 붙인 것이 아니다. 갈림길이라는 사용자 문제를 풀기 위해 에이전트가 작동한다.

**개발 우선순위** [합의]
1. 상태 변경 → 영향 정책 찾기 → 에이전트 출동 → 카드 갱신의 한 흐름 완성
2. 고정 처리 대 에이전트 비교 실험으로 에이전트의 실질적 기여 증명
3. 정책별 근거와 기준일을 보여줘 결과의 신뢰성 확보
4. "확인 불가"와 "재검토 필요"를 정직하게 표현하고, 신청 등 다음 행동으로 연결

**갈림길이 질문을 만들고, 에이전트가 답을 찾아온다.** 사용자가 상태를 바꾸면 코드가 바뀌는 정책을 골라낸다. 코드만으로는 대부분 "재검토"라는 같은 답밖에 못 낸다. 에이전트가 그 정책들의 공식 공고를 찾아가 "그 변화를 어떤 기준으로 보는지"를 확인해 와야 정책마다 다른 답과 다음 행동이 나온다. 예: 인천 응시료는 "응시일 현재 미취업", k-뉴딜은 "신청일 현재, 개시일 전 해소 시 가능", 청년도전은 "신청일로부터 6개월 이내 훈련 이력 없음", 드림For는 "2025.1.1부터 동일기업 재직". 넷 다 코드로는 "재검토"지만 실제 답은 모두 다르다.

포지셔닝: "AI 정책 추천"으로 경쟁하지 않는다. 대회 주제(청년의 일·생활 문제)에 맞게 사용자 문제를 앞에 두고, "공식 근거까지 추적하는 에이전트"를 그 문제를 푸는 방법으로 내세운다. 데이터 검증만 앞세우면 데이터 품질 도구처럼 보이고, 갈림길만 앞세우면 코드 필터처럼 보인다.

**두 가지 AI 역할**
- **정책 검증 에이전트** (핵심): 공개 정책 하나를 맡아, API가 준 링크가 정말 그 정책의 공식 공고인지 판단하고, 아니면 공식 출처에서 찾아가고, 찾은 자료를 다시 평가해 근거가 충분할 때만 조건을 대조한다. 끝내 못 찾으면 "확인 불가"로 남긴다. 개인정보를 쓰지 않으므로 누구에게나 실시간으로 돈다.
- **상담 에이전트** (보조): 가상 인물 시연에서 불확실성을 분석하고 질문을 골라 행동 카드를 만든다.

**대상 사용자** [합의]
교육과정 수료를 앞둔 미취업 청년. 진로는 계속 구직, 취업, 창업 세 갈래로 본다.

**풀려는 문제**
청년 정책은 취업 상태로 자격이 갈린다. 미취업자만 신청할 수 있는 정책은 취업하거나 사업자등록을 하면 닫히고, 직업훈련을 받는 중에는 신청할 수 없는 정책도 있다. 정책마다 "어느 시점의 상태를 보는지"가 다르고(신청일, 사업 개시일 등), 다른 정책에 참여 중이면 신청이 막히는 경우도 있다. 이 조건들은 공고문 본문에 흩어져 있어 청년이 직접 읽고 판단하기 어렵다. 기존 서비스는 지금 조건으로 받을 수 있는 것을 찾아주거나 자격이 바뀐 뒤 알려준다. 상태가 바뀌기 전에 "무엇이 닫히고 무엇이 열리는지, 무엇을 먼저 확인해야 하는지"를 보여주는 곳은 없다고 본다. [미확인] 기존 서비스는 직접 써보고 확인해야 한다.

**이 방식을 고른 이유** [합의]
1. 에이전트여야 한다.
2. 범용 AI에 한 번 물어서 되는 일이면 안 된다.
3. 공식 API 데이터를 중심에 둔다.
4. 미래를 본다. **상태 변화 기반 미래 시뮬레이션**: 청년이 교육 수료, 취업, 창업 같은 커리어 전환을 겪었을 때 정책 자격이 어떻게 달라지는지 시뮬레이션한다. 미래를 날짜로 예측하지 않고, 미래의 선택지를 비교한다.
5. 나 자신을 복제한다. 현재 상태의 복제본에 사건을 적용해 바뀐 복제본과 비교한다.
6. 취업이나 창업을 언제 하라고 권하지 않는다. 선택의 결과를 보여주되 선택을 대신하지 않는다.

## 2. 목표, 하지 않는 것, 실패로 보는 것

**목표**
- 최소 프로필(5개 항목)을 입력하면 정책을 "조건상 해당 / 확인 필요 / 조건상 비해당"으로 나눠 바로 보여준다.
- 상태 변화(수료, 취업, 사업자등록)를 고르면 재검토할 정책과 새로 검토할 정책을 비교해 보여준다. "수료 후 6개월" 같은 시간 조건은 이벤트 날짜로 계산한다.
- 정책 원문에 적힌 중복 참여 제한 문구를 그대로 보여준다.
- "확인 필요"가 많을 때, 답하면 가장 많은 정책의 판정이 바뀌는 질문 하나를 골라 선택적으로 묻는다.
- 정책별 행동 카드로 "지금 할 일 / 상태가 바뀌면 확인할 일 / 아직 모르는 조건"을 정리한다.
- 모든 판정에 원문 인용과 링크를 붙인다.

**하지 않는 것**
- 미래 공고 날짜의 예측. 과거 공고 이력은 "이력"으로만 보여준다.
- 12개월 타임라인, 사건 시점 탐색, 이사 시뮬레이션.
- 정책 쌍 단위의 중복 수혜 관계 엔진과 자동 잠금.
- 소득 간이 판정(중위소득 구간 선택으로 자격 확정).
- 지원 금액 합산, 수혜액 비교, 취업·창업 시점 추천.
- 로그인, 신청 대행, 알림, 서류 업로드.
- 제출본에서의 자동 수집 [합의].

**이렇게 되면 실패**
- 자격이 안 되는 정책을 "조건상 해당"으로 보여준다.
- 자격이 될 수 있는 정책을 "조건상 비해당"으로 보여준다. 원문 조건의 정의가 분명하지 않은데 비해당으로 확정하면 사용자가 받을 수 있는 정책을 놓친다. 예: "직업훈련 수강 중 제외"인데 사용자의 과정이 그 정책이 말하는 직업훈련인지 원문이 정의하지 않으면 "확인 필요".
- 상태가 바뀌었다고 기준일이 확인되지 않은 정책을 바로 "비해당"으로 바꾼다.
- 원문에 제한 문구가 없다는 이유로 "중복 가능"이라고 말한다.
- 취업을 미루거나 서두르라고 권하거나, 자격을 맞추는 요령을 안내한다.
- 실제 개인정보가 외부 AI로 전송된다.

  - 개인이 신청하지 않는 사업(위원회, 기업 장려금, 인프라)이 섞여 있다.
  - 취업 요건 코드와 본문이 어긋나는 경우가 있다. 예: 청년장병 취·창업 지원은 코드가 미취업자인데 본문 대상은 "병, 초급간부".
  - 나이 항목이 비었지만 본문에 나이가 적힌 경우, 나이 코드가 잘못 입력된 경우가 있다.
  - `(예비)창업자` 코드는 예비 단계와 등록 후를 구분하지 못한다.
  - 유효 정책 중 중복·유사 사업 제한을 본문에 적은 것은 60건, 다른 사업 이름을 구체적으로 적은 것은 약 13건이다.
  - 같은 이름의 정책이 여러 건 있다(중앙과 지자체 판, 연도별 판).
- [미확인] 지역 코드 체계의 공식 대응표, 온통청년 이용약관.

## 4. 검토한 방식

| 방식 | 내용 | 판단 |
|---|---|---|
| 시간축 시뮬레이션 (1~3판) | 사건 날짜를 받아 12개월을 월별 판정 | 버림. 사용자가 통제할 수 없는 날짜를 요구하고, 기간형 공고가 연말에 몰려 뒤가 비며, 시점 탐색은 "늦춰라"로 수렴 |
| **상태 전이 (4판)** | 현재 상태와 바뀐 상태를 각각 판정해 비교 | **선택** [합의]. 날짜 예측 불필요, 시점 권유 문제가 구조적으로 사라짐, 구현량 감소 |
| 정책 관계 엔진 | 정책 쌍별 중복 제한 관계표와 자동 잠금 | 버림 [합의]. 본문에 근거가 있는 정책이 적어 관계표를 채울 수 없음 |

핵심 원칙(1판부터 유지): **판정과 계산은 코드, 읽고 설명하고 다음 확인을 고르는 일은 AI.**

## 5. 구조

```
[온통청년 API] → ①수집·정제 → 원본 스냅샷(기준일 고정)
                      │
                      ├→ 데이터 3층(검증 / 부분 검증 / 과거 이력)
                      └→ ②핵심 정책 구조화(AI 추출 + 사람 검증)
                                     │
[사용자 5개 항목] → ③판정기(코드) ←──┘
                      │
                      ├→ ④상태 전이 비교(코드)
                      └→ ⑤에이전트: 불확실성 분석, 선택적 질문, 행동 카드
                                     │
                               ⑥화면: 입력 / 결과 / 상태 변경 / 행동 카드
```

### ① 수집·정제
- 전체를 받아 원본 스냅샷으로 보관한다. 실패한 쪽은 3회까지 재시도한다.
- 정제: 빈 값 통일, 날짜 파싱, 지역 코드 분해.
- 원본 정책은 고유 번호(`plcyNo`)별로 그대로 보존한다. **판정에는 개별 공고의 조건만 쓴다.** "연도·차수 표기를 뗀 명칭 + 주관기관"으로 같은 사업을 묶는 것은 과거 이력 화면의 표시에만 쓴다. 연도마다 대상·소득 기준·지역이 바뀔 수 있어서 묶어서 판정하면 조건이 섞이기 때문이다.
- 신청 주체 1차 분류(규칙 기반): 명칭과 제공 방법 코드로 기업·기관·인프라 사업을 걸러낸다. 핵심 정책은 ②에서 다시 확인한다.

**데이터 3층**

| 층 | 대상 | 화면에서의 쓰임 |
|---|---|---|
| 검증 정책 | 핵심 정책 **12~15건**(시연 6건 + 전국 단위 중앙 정책 위주). 검증 에이전트가 초안과 불일치 목록을 만들고 사람이 확정 | 확정 판정, 상태 전이 비교, 행동 카드 |
| 부분 검증 정책 | 그 밖의 유효·개인 신청형 정책 | 코드 조건으로 판정. 별도 자격 항목이 비어 있으면 "코드 조건 충족(본문 미검토)", 있으면 "확인 필요". 화면에서 "검증 요청" 버튼으로 검증 에이전트를 돌릴 수 있음 |
| 과거 이력 | 신청 기간이 지난 정책 | 현재 판정에 쓰지 않음. "○년 ○월에 공고된 적 있음"으로만 보여줌 |

검증 정책을 인천 지역 사업이 아니라 전국 단위 중앙 정책 위주로 고르는 이유: 심사위원이 어느 지역 프로필을 넣어도 확정 판정이 몇 건은 나와야 한다. 27세 미취업 인물 기준 코드상 해당 정책은 서울 197건, 대전 186건, 인천 216건, 경북 포항 221건이고, 그중 52~57%는 별도 자격 항목이 비어 있다(2026-11-16 집계).

과거 이력의 집계 수치를 화면에 낼 때는 무엇을 셌는지(레코드 수, 같은 사업을 묶은 수, 개인 신청형만, 미취업 조건이 원문에서 확인된 것만)를 함께 적는다. 집계를 마치기 전에는 숫자를 내지 않는다.

### ② 정책 검증 에이전트 (핵심 AI): 공식 공고를 찾아가 대조한다

**핵심은 공고 찾아가기다.** API가 준 링크는 그대로 믿을 수 없다. 2026-11-16 시연 정책 6건을 대조할 때 4건은 링크를 열어서 끝나지 않았다(첫 화면이라 찾아 들어감, 다른 하위 과정이라 다시 찾음, 접속 오류라 우회). 유효 정책 1,471건 중 링크가 사이트 첫 화면 241건, 없음 22건, 민간·SNS 18건으로 약 19%다. 주소가 상세 페이지 모양이어도 다른 사업을 가리키는 경우가 있다(몇 건인지는 모름).

**에이전트라고 말하는 근거**: 경로가 여러 개라는 사실이 아니다. 분기 자체는 조건문으로도 짤 수 있다. 근거는 **관찰 → 판단 → 행동 → 재평가**의 반복이다. 특히 "이 페이지가 원래 정책과 같은 사업의 공고인가"와 "지금 가진 근거로 충분한가"는 형식이 제각각인 페이지를 읽고 내리는 판단이라 조건문으로 대신하기 어렵다. [외부 평가 반영]

**실행 구조**

1. **API 링크 접속**: 원본 링크에서 페이지와 사업 정보를 읽는다.
2. **페이지 적합성 판단**(AI): 사업명·연도·주관기관을 확인해 "정상 공고 / 첫 화면 / 다른 사업 / 접속 오류" 중 하나로 판단하고, 근거 문장을 남긴다.
3. **다음 행동 선택**(AI):
   - 정상 공고 → 조건 추출로
   - 첫 화면 → 공식 사이트 안에서 검색
   - 다른 사업 → 같은 사업의 공식 공고를 다시 찾기
   - 접속 오류 → 다른 공식 출처(정부24, 온통청년, 지자체 청년포털 등) 찾기
4. **탐색 결과 재평가**(AI): 새로 찾은 자료가 원래 정책과 같은 사업인지 다시 확인한다. 아니면 3으로.
5. **종료 판단**(AI + 코드 한도): 근거가 충분하면 조건 대조로. 탐색 한도에 닿으면 "공식 공고 확인 불가"로 끝낸다. 억지로 비슷한 공고를 근거로 쓰지 않는다.
6. **조건 대조와 제출**: 조건 추출(AI) → 인용 검사(코드) → API와 공고 비교(AI가 읽고 날짜·지역 비교는 코드) → 사람 검토 대기열.

**역할 분담**: 탐색 경로 선택, 같은 사업인지 판별, 근거 충분성 판단은 에이전트가 한다. 접근 범위와 안전장치, 최종 자격 판정은 코드와 사람이 통제한다.

| 통제 | 방식 |
|---|---|
| 허용 도메인 | 정부(`go.kr`), 공공기관, 지자체, 온통청년, 그리고 그 정책 주관기관의 공식 사이트. 그 밖은 열지 않음(코드) |
| 탐색 한도 | 정책 하나에 페이지 열기 최대 6회, 검색 최대 3회, 60초(코드) |
| 수집 범위 | 요청이 있을 때 정책 하나씩. robots.txt 준수. 결과는 정책 번호별로 저장해 다시 열지 않음(코드) |
| 첨부파일 | HTML 페이지만 읽음. 한글(HWP)·PDF 첨부만 있으면 "첨부 확인 필요"로 표시 |
| 최종 판정 | 에이전트 결과는 초안. 사람이 검토해야 확정 판정에 쓰임 |

[미확인] 공식 도메인 안에서 검색하고 여러 페이지를 여는 것이 대회 규칙의 "무단 수집"에 해당하지 않는다고 판단하지만, 링크 하나를 여는 것보다 수집에 가까워진다. 위 한도를 지키는 조건이고 해석이다.

[미확인] 검색 수단: Claude API의 웹 검색·웹 가져오기 도구를 허용 도메인 제한과 함께 쓰는 것을 우선 검토한다. 구현 전에 현재 문서로 사용법과 제한 옵션을 확인한다.

**시연**: 세 정책을 돌려 서로 다른 판단을 보여준다. 도구 호출 기록에 판단 근거가 함께 보인다.

| 정책 | 보여줄 판단 | 증명하는 것 |
|---|---|---|
| 인천 자격증 응시료 | 링크가 바로 맞는 공고. 탐색하지 않고 대조로 | 불필요한 탐색을 하지 않음. 공고에만 있는 "응시일 현재 미취업자" 탐지 |
| 직장인 든든한 점심밥 | 링크가 농식품부 첫 화면 → aT 사업 사이트를 찾아감 | 탐색 경로 선택. 시행 지역 불일치(인천 없음) 탐지 |
| 바이오전문인력양성 | 링크의 공고가 다른 하위 과정임을 판별 → 같은 사업의 공고를 다시 찾음 | 잘못된 근거를 배제하고 재탐색. 다시 찾은 결과까지 보여줌 |

바이오는 재탐색 결과가 무엇인지 아직 모른다. 산업통상부·한국바이오협회의 사업 공고를 찾으면 그것으로 대조하고, 못 찾으면 "공식 공고 확인 불가"로 끝나는 것이 맞는 동작이다. 어느 쪽인지 11/18에 미리 확인해 시연 대본을 정한다.

**평가 지표** (정답 세트로 측정)

| 지표 | 내용 |
|---|---|
| 원본 링크 성공률 | API 링크만으로 공식 공고를 확인한 비율 |
| 재탐색 성공률 | 원본 링크가 부적절할 때 대체 공고를 찾은 비율 |
| 같은 사업 판별 정확도 | 관련 사업과 같은 사업을 바르게 구분한 비율 |
| **잘못된 근거 채택률** | 다른 사업의 공고를 원래 정책의 근거로 쓴 비율. 0이 목표 |
| **종료 적절성** | 공고가 없거나 찾을 수 없을 때 "확인 불가"로 끝낸 비율 |

정답 세트: 시연 6건 + 링크가 첫 화면·없음·민간인 정책에서 고른 6~9건, 총 12~15건. 사람이 정책마다 "맞는 공식 공고 주소" 또는 "찾을 수 없음"을 적어 둔다. 무조건 찾아내는 것보다 잘못된 공고를 근거로 쓰지 않는 것이 더 중요하다.

**비교 실험: 고정 처리 대 에이전트** [합의]
같은 정답 세트에 두 방식을 돌려 위 다섯 지표와 비용을 비교한다. AI 활용 적절성(25점)에서 "에이전트가 더 나은 결과를 낸다"를 숫자로 보여주기 위해서다.

| 방식 | 내용 |
|---|---|
| 고정 처리 | API 링크만 열어서, 그 페이지로 조건 추출과 비교를 한 번씩 한다. 페이지가 맞는지 판단하거나 다시 찾지 않는다 |
| 에이전트 | 위 실행 구조 |

비교 항목: 다섯 지표 + 정책당 AI 호출 수, 열어 본 페이지 수, 걸린 시간, 비용. 결과가 에이전트에 불리하게 나와도 그대로 적는다. 예상(추측): 링크가 맞는 정책에서는 두 방식이 같고, 링크가 첫 화면·다른 사업인 정책에서 차이가 난다. 고정 처리는 다른 사업의 공고를 근거로 채택하는 경우가 생길 것이다.

**사람의 역할**: 에이전트 결과는 "초안"이다. 확정 판정에 쓰이려면 사람이 검토해 `human_verified`로 바꿔야 한다. 운영 시에는 수정일이 바뀐 정책만 에이전트가 다시 검증하고 사람은 불일치가 있는 것만 본다.

**추출 항목**: 원문에서 확인되지 않은 값은 비워 둔다. AI가 빈칸을 추정해 채우지 않는다.

| 항목 | 내용 |
|---|---|
| application_subject | 개인 / 기업·기관 / 제도 |
| status_conditions | 필요한 상태와 제외되는 상태(미취업, 고용보험 미가입, 직장가입자 제외, 사업자등록 제외, 직업훈련 수강 중 제외, 재학생 제외 등) |
| eligibility_reference_date | 취업·훈련 등 **상태**를 보는 시점(신청일, 응시일, 사업 개시일 등). 원문에 없으면 빈칸 |
| age_reference_date | **나이**를 세는 기준(예: "2026. 1. 1. 기준", "참여 신청일 현재")과 산정 방식(만 나이, 출생연도 범위). 상태 기준일과 섞지 않는다. 원문에 없으면 빈칸이고 나이 판정은 "확인 필요" |
| lookback_condition | 과거 이력 조건(예: 신청일 이전 6개월 이상 교육·훈련 이력 없음) |
| age, region_scope | 원문 기준 나이와 거주 요건 |
| income_condition | 원문 인용과 산정 기준(가구·본인, 중위소득 등). 판정에는 쓰지 않음 |
| restriction_quotes | 중복 참여·유사 사업 제한 문구 원문 |
| named_restrictions | 제한 문구에 이름이 나온 다른 정책(예: 국민취업지원제도) |
| source_quote, source_url | 근거 문장과 출처 |
| verification_status, last_verified_at | 사람 검증 여부와 날짜 |

- 인용 문장이 원문에 실제로 있는지 코드로 검사한다.
- 공식 공고 페이지와 API 본문이 다를 수 있으므로, 핵심 정책은 가능하면 원 공고 링크까지 확인하고 `verification_status`에 어디까지 확인했는지 남긴다.

### ③ 판정기 (코드)

**판정은 네 개의 축으로 따로 계산하고 따로 보여준다.** 한 줄로 합치면 "모집이 끝난 정책"이 "자격이 없는 정책"처럼 보이기 때문이다.

| 축 | 값 | 무엇으로 정하나 |
|---|---|---|
| 개인 자격 | 조건상 해당 / 조건상 비해당 / 확인 필요 | 프로필, 상태, 원문 조건 |
| 모집 상태 | 모집 중 / 모집 예정 / 모집 종료 / 상시 / 기간 확인 필요 | 신청 기간과 **접속한 날** |
| 시간 조건 | 충족 / 미충족 / 확인 필요 / 해당 없음 | 이벤트 이력과 정책별 기간 조건(예: 최근 6개월 훈련 이력 없음) |
| 제한 사항 | 원문 제한 있음 / 확인된 관계 있음 / 없음으로 확인 / 미확인 | ②의 제한 문구와 사람 검증 |

개인 자격 축의 규칙

| 값 | 조건 |
|---|---|
| 조건상 해당 | 검증 정책이고, 확인된 조건을 모두 만족하며, 소득 조건이 없음 |
| 코드 조건 충족(본문 미검토) | 부분 검증 정책이고, 코드 조건을 만족하며, 별도 자격 항목(추가 자격, 참여 제한, 소득)이 비어 있음. 지원 내용·설명 본문에 조건이 숨어 있을 수 있어 "해당"이라고 하지 않는다 |
| 확인 필요 | 부분 검증 정책인데 별도 자격 항목이 있거나, 소득 조건·기준일 미확인·코드-본문 충돌·프로필에 없는 값이 있음 |
| 조건상 비해당 | 확인된 조건 하나 이상을 확실히 불만족하고, 그 조건의 정의가 원문에서 분명함. 정의가 불분명하면 "확인 필요". 사유를 기록 |

**날짜 규칙**
- 모든 날짜는 한국 시간(Asia/Seoul) 기준이다. 서버 시간대와 상관없이 같은 결과가 나와야 한다.
- 종료일이 날짜 단위로만 있으면 **종료일 당일 24시까지 모집 중**으로 본다. 검증 정책에 공식 공고의 마감 시각이 있으면(예: 18시) 그 시각을 쓴다.
- 신청 기간 구분이 "상시"이거나 신청 기간이 비어 있으면 모집 종료로 처리하지 않는다. 상시면 "상시", 비어 있으면 "기간 확인 필요".
- 사업 종료일(`bizPrdEndYmd`)이 지난 상시 정책은 "기간 확인 필요"로 둔다.
- 화면에는 "데이터 기준일"과 "판정 기준일(오늘)"을 따로 표시한다.

- 지역: 프로필의 시군구 코드가 정책 지역 코드에 있어야 한다. 지역 코드가 15개 이상 시도에 걸쳤는데 주관기관이 지자체면 주관기관 이름의 시도로 다시 좁힌다.
- 나이: 코드 값을 쓰고, 비어 있으면 검증 정책은 ②의 값, 부분 검증 정책은 "확인 필요".
- 모든 항목은 없을 수 있다고 보고 처리한다.
- 판정은 우리 서버 코드에서 한다. 외부 AI는 판정에 관여하지 않는다.

### ④ 상태 전이 비교 (코드)

**상태와 이벤트를 나눈다** [제안, 외부 의견 반영]

상태만으로는 "신청일 이전 6개월 이상 교육·훈련 이력이 없을 것" 같은 조건을 판정할 수 없다. 수료 직후에는 여전히 조건을 못 채우기 때문이다. 그래서 세 가지를 따로 둔다.

| 구분 | 내용 | 예 |
|---|---|---|
| 현재 상태 | 지금의 상태 | 교육 수강 중, 미취업, 대학 졸업, 사업자등록 없음 |
| 이벤트 이력 | 상태를 바꾼 사건과 그 날짜 | 교육 수료일, 취업일, 사업자등록일 |
| 정책별 시간 조건 | ②에서 원문으로 확인한 기준 | 신청일 기준 최근 6개월, 신청일 기준 고용보험 미가입, 선정일 기준 미취업 |

최종 판정 = 현재 상태 + 이벤트 이력 + 정책별 기준일.

- 이벤트 날짜는 **이미 일어났거나 일정이 정해진 사건**에만 받는다. 앞으로 언제 취업할지 같은 날짜는 묻지 않는다.
- 이벤트에는 상태를 붙인다.

```json
{"event_type": "training_completion", "event_date": "2026-11-30", "event_status": "scheduled"}
```

  - `scheduled`(예정): 과정 일정으로 정해진 수료 예정일 등. 현재 판정에서는 **아직 일어나지 않은 것**으로 본다. 시간 조건의 기간 계산(예: 수료일부터 6개월)에 쓸 때는 "예정일 기준"이라고 표시한다.
  - `completed`(완료): 실제로 일어난 사건. 사용자가 확인하면 예정에서 완료로 바꾼다.
- 상태 변경 버튼은 "**오늘** 이 사건이 일어났다고 가정"하는 시뮬레이션이다. 3개월 뒤 취업 같은 미래 시점은 지원하지 않는다(시점 탐색이 "늦춰라"로 수렴했던 문제를 피하기 위한 의도된 제한). 소개서와 화면에서는 "미래의 정책이나 공고 시점을 예측하지 않고, 사용자가 고른 커리어 상태 변화가 정책 자격에 주는 영향을 비교한다"고 쓴다. 누르면 가정 이벤트(`simulated`)를 판정 기준일 날짜로 넣고 비교한다. 가정 이벤트는 저장된 프로필을 바꾸지 않는다.
- 상태 종류
  - 교육·훈련: 수강 중 / 수료
  - 일: 구직 중 / 취업 상태(기업 규모: 중소·중견·대기업·공공·모름) / 예비창업 / 사업자등록 완료
  - 정책이 실제로 구분하는 조건에만 연결한다. "취업"이 최종 합격인지, 근로계약인지, 출근인지, 고용보험 취득인지는 정책마다 다르므로, 내부에서 나누지 않고 정책별 원문 기준(②의 `eligibility_reference_date`, `status_conditions`)으로 판단한다. 원문에 기준이 없으면 "재검토 필요"로 둔다.

**전이 결과의 표현**

| 결과 | 의미 | 화면 문구 |
|---|---|---|
| 자격 재검토 | 바뀐 상태에서 원문 조건을 못 채울 가능성이 있음 | "취업 상태에서 자격 재검토" |
| 기준일 확인 필요 | 상태 조건과 충돌하지만 어느 시점을 보는지 원문에 없음 | "자격 판단 기준일 확인 필요" |
| 조건 충족 시 신청 가능 | 바뀐 상태와 이벤트 이력으로 조건을 채움 | "수료 이력 조건 충족 시 신청 가능" |
| 기간 경과 후 재검토 | 과거 이력 조건 때문에 일정 기간 뒤에 가능 | "수료일 기준 6개월 경과 후 재검토" |
| 유지 | 상태와 무관 | 표시 안 함 |

- "닫힘", "열림"처럼 확정하는 말은 쓰지 않는다.
- 다른 정책 참여 제한(예: "국민취업지원제도에 참여하여 수혜 중인 자")은 원문 문구로 보여주고, 사용자가 그 정책에 실제로 참여 중이라고 답하지 않은 한 자동으로 비해당으로 바꾸지 않는다.
- 시간은 보조 정보로 남긴다: 현재 공고의 신청 마감일(30일 이내면 강조), 과거 공고 이력, 기간 경과 조건.
- **마감 여부는 데이터 기준일이 아니라 접속한 날 기준으로 계산한다.** 데이터는 11/23로 고정돼도, 11/30 마감 정책은 12/1부터 "모집 종료"로 보여야 한다. 계산 규칙은 제출 때 고정되므로 마감 후 변경 금지 규칙과 충돌하지 않는다.
- 상태 전이 비교는 개인 자격 축과 시간 조건 축에만 적용한다. 모집 상태는 상태 변화와 무관하다.
- 취업 상태로 바꿔도 모든 정책을 한꺼번에 비해당으로 바꾸지 않는다.
  - 검증 정책: 원문에서 확인된 상태 조건으로 판단한다.
  - 부분 검증 정책: 취업 요건 코드가 바뀐 상태와 맞지 않으면 "**자격 재검토(코드 기준, 본문 미확인)**"로 표시한다. 미취업자 코드 정책(인물마다 약 20건)이 여기에 해당한다. 상태 전이의 핵심 장면이 검증 정책 안에서만 보이지 않게 하기 위해서다.

**상태가 바뀌면 에이전트가 출동한다** [합의]
1. 상태 변경 결과 중 "자격 재검토(코드 기준)", "자격 판단 기준일 확인 필요"인 정책을 코드가 모은다.
2. 그중 검증 결과가 저장돼 있지 않은 정책에 정책 검증 에이전트를 돌린다(화면 상단에 "N건 공식 공고 확인 중"). 한 번에 최대 5건, 나머지는 사용자가 카드에서 요청.
3. 에이전트는 정책의 상태 관련 조건 전체(수료·취업·사업자등록에 걸리는 기준일과 정의)를 확인해 온다. **요청에는 정책 번호만 들어간다.** 에이전트는 어떤 사용자가 어떤 상태로 바꿨는지 모른다. 어떤 변화에 적용할지는 우리 코드가 판단한다.
4. 결과가 오면 카드가 "재검토"에서 구체적인 문장과 다음 행동으로 바뀐다. 에이전트 결과는 초안이므로 카드에 "공식 공고 기준 AI 확인(사람 검토 전)"을 표시하고, 개인 자격 축은 사람 검토 전까지 "확인 필요"를 넘지 않는다. 대신 확인된 기준일과 원문 인용, 다음 행동은 바로 보여준다.
5. 결과는 정책 번호별로 저장해 다음 사용자는 기다리지 않는다.

### ⑤ 상담 에이전트 (보조, 가상 인물 시연 전용)

**하는 일**: 가상 인물의 판정 결과에서 중요한 불확실성을 찾고, 다음에 확인할 것을 정하고, 행동 카드를 만든다. 자격 판정은 하지 않는다.

**대표 질문**: "국민취업지원제도에 참여 중인가요?" (예 / 아니오 / 모름). 답에 따라 청년도전지원사업의 참여 제한 조건이 실제로 적용되는지가 바뀐다. 질문이 판정을 바꾸는 장면을 보여주는 사례다. 국비 교육 수강생 중 참여자가 많다는 것은 일반적인 인식이며 확인하지 않았다.

실제 사용자 모드의 행동 카드는 검증 정책용 템플릿(정책별 확인 순서와 근거)을 코드가 조립한다. 템플릿은 검증 에이전트가 만든 초안을 사람이 확정할 때 함께 만든다.

**흐름**
1. 입력 직후 판정 결과를 바로 보여준다(질문 없이).
2. 불확실성 분석: `rank_open_questions`가 "확인 필요"의 원인을 조건 종류별로 세어 질문 후보를 돌려준다. 후보마다 관련 정책 수, 답에 따라 판정이 바뀔 수 있는 정책 수, 답해도 여전히 확인이 필요한 정책 수를 코드가 계산한다.
3. 선택적 질문: 에이전트가 후보 중 하나를 골라, 관련 정책 원문을 `get_policy_evidence`로 읽어 질문이 실제 조건과 연결되는지 확인한 뒤 묻는다. 사용자는 답하거나 건너뛸 수 있다. 답은 선택지로만 받는다.
4. 상태 변경이 들어오면 `simulate_transition`을 호출하고 결과를 해석한다.
5. 행동 카드를 만든다.

**도구**

| 도구 | 기능 | 실행 |
|---|---|---|
| search_policies | 현재 상태로 판정한 정책 목록 | 코드 |
| get_policy_evidence | 정책 원문, 구조화 항목, 제한 문구 | 코드 |
| rank_open_questions | 질문 후보와 영향 수치 | 코드 |
| simulate_transition | 상태 변화 전후 비교(이벤트 이력 포함) | 코드 |
| ask_user | 선택지 질문 | 화면 |

**행동 카드** (정책마다)
- 현재 확인된 사항: 지금 상태에서 확인된 조건, 신청 마감일
- 다음에 확인할 사항: **먼저 풀어야 할 불확실성부터 순서대로**(예: 실제 수료일 → 신청일 기준 6개월 훈련 이력 → 참여 제한 조건)
- 판단 근거: 왜 이 순서인지, 어떤 원문 조건과 연결되는지
- 원문 제한 문구와 원문 링크

이 카드에서 에이전트가 하는 일은 새 정책 추천이 아니라 **어떤 불확실성을 먼저 풀어야 하는지 정하는 것**이다. `rank_open_questions`와 `get_policy_evidence`로 만든다.

**금지 사항** (시스템 프롬프트에 명시)
- 자격을 스스로 판정하지 않는다. 도구 결과만 인용한다.
- 금액·날짜를 계산하거나 지어내지 않는다.
- "확인 필요"를 확정처럼 말하지 않는다.
- 원문에 제한 문구가 없다고 "중복 가능"이라고 말하지 않는다.
- 취업·창업을 미루거나 서두르라고 권하지 않는다. 어느 쪽이 유리하다는 비교를 하지 않는다.
- 소득·주소·신분을 바꿔 자격을 맞추는 방법을 권하지 않는다.
- 선정된다고 말하지 않는다.

### ⑥ 화면
1. **입력** (5개 항목 + 선택 1개): **생년월**, 거주 시군구, 현재 상태, 학력, 관심 있는 전환(계속 구직 / 취업 / 창업). 교육 수강 중이거나 수료했으면 수료(예정)일을 선택 입력으로 받는다. 시연용 가상 인물 버튼. 연령대로는 "2026. 1. 1. 기준 만 39세 이하" 같은 조건을 판정할 수 없어 생년월로 바꿨다. 생년월은 판정 코드에만 쓰고 외부 AI로 보내지 않는다. 생년월만으로는 기준일이 생일 달과 겹칠 때 만 나이가 하나로 정해지지 않으므로, 그 경우가 나이 상·하한 경계와 겹치면 "확인 필요"로 둔다. 개인정보 수집을 줄이기 위해 생년월일은 받지 않는다. [합의]
2. **결과**: 조건상 해당 / 코드 조건 충족(본문 미검토) / 확인 필요 / 조건상 비해당 건수와 목록. 30일 안에 마감되는 정책을 위에 둔다. 카드 앞면에는 **"자격"과 "모집" 두 축만** 보이고, 시간 조건과 제한 사항은 카드를 열면 보인다. 부분 검증 정책 카드에는 "검증 요청" 버튼(정책 검증 에이전트 실행).
2-1. **정책 검증 화면**: 정책을 고르면 검증 에이전트가 단계별로 무엇을 했는지(도구 호출 기록), 찾은 불일치, 출처 링크를 보여준다. 심사위원이 정책을 직접 고를 수 있다.
3. **선택적 질문**: 결과 위에 한 줄로 "가구원 수를 알려주시면 ○개 정책을 더 구체적으로 검토할 수 있습니다"처럼 표시하고 건너뛸 수 있게 한다.
4. **상태 변경**: "수료 상태로 변경", "취업 상태로 변경", "사업자등록 상태로 변경" 버튼. 차례로 누를 수 있고, 누를 때마다 이전 상태와 비교해 ④의 결과 표현으로 나눠 보여준다.
5. **행동 카드**: 정책을 누르면 카드가 열린다.
6. **에이전트 작업 기록**: 어떤 도구를 왜 불렀는지 접어서 보여준다.

화면 하단에 고지를 한 줄로 둔다: "데이터 기준일 2026-11-23 · 모집 상태는 오늘 기준 · 이후 신규·변경 공고 미반영 · '조건상 해당'은 선정을 보장하지 않으며 최종 자격은 담당 기관에서 확인하세요". 누르면 전체 설명이 펼쳐진다. AI가 만든 문장 옆에는 작은 "AI 생성" 표시를 붙인다.

## 7. 개인정보와 보안

**원칙: 사용자가 입력한 정보와 거기서 나온 정보(상태, 개인별 판정 결과, 질문 답변)는 외부 AI에 보내지 않는다.** [외부 평가 반영] 이름을 빼도 "이 사람은 수강 중이고 이 정책은 비해당"은 특정 사용자의 상황에서 만들어진 정보다. 대회 규칙을 보수적으로 해석한다.

이 원칙 아래에서 AI를 쓰는 방법은 두 가지 모드로 나눈다. [합의, 2026-11-16 확정]

| 모드 | 언제 | 외부 AI에 가는 것 | AI가 하는 일 |
|---|---|---|---|
| **실제 사용자** | 사용자가 자기 정보를 입력했을 때 | 사용자와 무관한 공개 정책 원문과 공식 공고만(검증 요청을 눌렀을 때) | **정책 검증 에이전트는 실시간으로 돈다.** 사용자 판정과 행동 카드는 코드와 검증 정책 템플릿으로 만든다 |
| **가상 인물** | 시연용 가상 인물 버튼으로 시작했을 때 | 가상 인물의 상태와 판정 결과, 공개 정책 원문 | 정책 검증 에이전트 + 상담 에이전트(질문 선택, 행동 카드) |

정책 검증 에이전트의 요청에는 정책 번호와 공개 데이터만 들어간다. 어떤 사용자가 검증을 요청했는지, 그 사용자의 판정 결과는 들어가지 않는다.

- 가상 인물은 대회 규칙이 허용하는 "가상·샘플 데이터"다. 화면에 현재 모드를 표시한다.

**서버에서의 격리** (화면 구분만으로는 부족하다)

| 항목 | 실제 사용자 | 가상 인물 |
|---|---|---|
| 판정·상태 전이·행동 카드 경로의 외부 AI 호출 | **금지(0회)** | 허용(상담 에이전트) |
| 정책 검증 에이전트 | 허용. 요청에는 정책 번호와 공개 데이터만 | 허용 |
| 프로필 전송 | 금지 | 서버에 미리 정의된 가상 인물 프로필만. 브라우저는 **가상 인물 번호만** 보낸다 |
| 자유 텍스트 입력의 AI 전송 | 기능 없음 | 기능 없음. 질문 답은 선택지 번호로만 |
| 개인별 자격 판정 | 코드 | 코드 |
| 행동 카드 | 사전 생성 문장 + 코드 조합 | 실시간 생성, 실패 시 사전 생성 문장으로 대체 |

- 에이전트 API는 요청 본문에 가상 인물 번호와 선택지 번호 외의 필드가 있으면 거부한다. 가상 인물 프로필은 서버 코드 상수에서만 읽는다. 사용자가 가상 인물의 항목을 하나라도 고치면 그 세션은 실제 사용자 모드가 된다.
- 외부 AI 호출 전체를 끄는 환경변수 스위치(`EXTERNAL_AI_ENABLED`)를 둔다. 꺼져 있거나 호출이 실패하면 사전 생성 문장으로 동작한다.
- 서버는 프로필을 저장하거나 로그에 남기지 않는다.
- 정책 검증 API는 요청 본문으로 정책 번호 하나만 받는다. 다른 필드가 있으면 거부한다.
- 자동 테스트(필수): 실제 사용자 모드의 판정·전이·카드 경로에서 외부 AI 호출 0회, 상담 에이전트 API가 프로필 필드가 든 요청을 거부, 가상 인물 요청의 내용이 서버 상수와 공개 원문뿐, 정책 검증 요청의 내용이 정책 번호와 공개 데이터뿐.

**공개 정책 원문의 외부 AI 전송**: 대회 「AI 활용 및 출처 표기 기준」 제3조가 "서비스 기능으로 LLM… API 연동, AI 에이전트 구성"을 허용 항목으로 두고, 금지 대상은 "실제 개인정보·민감정보"의 전송이다. 대회 주제 예시에도 "공공데이터와 생성형 AI를 활용한 문제 해결 서비스"가 있고, 온통청년 API는 "이용허락범위 제한 없음"이다. 그래서 공개 정책 원문 전송은 허용된다고 보고 진행한다. 사용자에게서 나온 정보는 어떤 모드에서도 보내지 않으므로 운영사무국 문의는 필수가 아니다. 다른 외부 평가에서는 사무국 확인 전까지 보류를 권했다. 판단이 바뀌면 위 스위치로 끈다.

**발표에서의 설명**
- 정책 검증 에이전트는 모든 사용자에게 실시간으로 돈다. 개인정보를 쓰지 않고 공개 정책과 공식 공고만 다루기 때문이다. 이 에이전트가 판정의 근거 데이터를 만든다.
- 개인별 판정은 코드가 한다. 그래서 사용자의 정보는 외부 AI로 가지 않는다.
- 상담 에이전트는 가상 인물로 시연한다. 운영사무국이 비식별 상태 정보의 전송을 허용하면 실제 사용자에게도 켤 수 있다.
- [선택] 11/17에 운영사무국에 "생년월 없이 연령대·시도·취업 상태만 보내도 되는가"를 문의한다. 답이 늦어도 설계는 그대로 동작한다.

| 구분 | 처리 |
|---|---|
| 사용자 프로필 | 식별 정보(이름, 연락처, 주민번호, 상세 주소) 수집 안 함. 생년월·시군구·상태·학력·수료일만 받음 |
| 개인별 판정·상태 비교 | 우리 서버 또는 브라우저의 코드. 저장하지 않음 |
| 외부 AI | 위 두 모드 표대로 |
| 시연·검증·소개서 화면 | 가상 인물만 |
| 질문의 답 | 선택지로만 받음 |

- 서버 로그, 분석 도구, 오류 추적 도구에 프로필이 남지 않게 한다.
- 대화 입력이 생기면 전화번호·주민번호·이메일 형태를 전송 전에 가린다.
- API 키는 서버 환경변수로만 다룬다.
- [미확인] 연령대·시군구 같은 비식별 값을 외부 AI에 보내도 되는지. 운영사무국에 문의한다.

## 8. AI 오류와 한계 대응

| 위험 | 대응 |
|---|---|
| AI가 본문 조건을 잘못 뽑음 | 핵심 정책은 사람이 원문 대조로 확정, 인용 검사, 미확인 값은 빈칸 |
| 코드와 본문이 어긋남 | 핵심 정책은 본문 우선, 부분 검증 정책은 "확인 필요" |
| AI가 판정이나 관계를 지어냄 | 판정은 코드만, 관계는 원문 인용만 |
| 상태가 바뀌었는데 기준일을 모름 | "기준일 확인 필요"로 분리 |
| 다른 지역·비개인 사업 노출 | 주관기관 기반 지역 재판정, 신청 주체 분류 |
| 부적절한 권유 | 금지 사항, 비교·추천 기능 없음 |

**알려진 한계 (소개서에 적는다)**
- 확정 판정은 검증한 핵심 정책 20~30건에만 한다. 나머지는 조건부 안내다.
- 소득 조건이 있는 정책은 확정하지 않는다.
- 정책 간 중복 제한은 원문에 적힌 것만 보여준다.
- 지역마다 데이터에 들어 있는 지역 정책 수가 크게 다르다(대전 8건, 경북 190건).
- 복제본의 동기화는 수동이다. 사용자가 상태를 바꿀 때 다시 분석한다.

- AI 활용내역 ④: 9장 검증 수치와 8장 알려진 한계.

  - "AI가 실제로 하는 일은 / 이게 정말 에이전트인가": "저희 에이전트는 조건을 추출하는 데서 그치지 않습니다. API가 준 링크가 실제 그 정책의 공식 공고인지 판단하고, 자료가 부족하거나 잘못됐으면 다음 탐색 경로를 고릅니다. 찾은 결과를 다시 평가해 근거가 충분할 때만 조건을 대조하고, 끝내 확인할 수 없는 것은 확인 불가로 남깁니다." 인천 응시료(바로 확인), 든든한 점심밥(찾아감), 바이오(다른 사업을 배제하고 재탐색)의 서로 다른 판단과 평가 지표(특히 잘못된 근거 채택률)로 보여준다.
  - "1,471건 중 일부만 검증했는데 운영은": 검증 에이전트가 초안과 불일치 목록을 만들고 사람은 불일치만 본다. 수정일이 바뀐 정책만 다시 검증한다.
  - "API가 상시인데 실제로 끝난 사례가 있었다면 다른 정책은 믿을 수 있나": 그래서 검증 에이전트를 만들었다. 사용자도 "검증 요청"으로 확인할 수 있다.
  - "서울 프로필은 전부 확인 필요 아닌가": 전국 단위 검증 정책과 "코드 조건 충족(본문 미검토)" 등급으로 어느 지역이든 결과가 나눠 보인다.
  - "결국 취업을 늦추라는 것 아닌가": 시점을 묻지도 권하지도 않는다. 상태가 바뀌면 무엇을 확인해야 하는지만 보여준다.

## 추가(2026-11-17): 상태 갈림길 루트와 "먼저 확인할 순서" 가중치

### 왜 추가했나
화면이 정책 목록에 머물러 "갈림길"이 보이지 않았다. 사용자가 기대한 그림은 정책 1→2→3→4가 이어지다 5, 6으로 갈라지는 길이다.

### 무엇을 하나
- **마디는 상태다.** 지금 → (수강 중이면) 수료한 뒤 → 갈림길(취업한다면 / 사업자등록을 한다면). 가정 마디는 "오늘 그 일이 일어났다고 가정"한 것이며 입력 프로필은 바꾸지 않는다(`lib/route/build.ts`).
- **마디 안의 번호는 "먼저 확인할 순서"다.** 첫 마디는 최대 4개, 다음 마디는 그 상태에서 새로 열리는 정책만 최대 3개. 한 길 위에서 같은 정책은 한 번만 나온다. 앞에서 본 정책이 그 상태에서 달라지면 "다시 볼 것"으로 따로 적는다.
- **가중치는 우리가 정한 규칙이다**(`lib/route/weight.ts`). 점수는 이유들의 합이고 화면에 이유와 점수를 그대로 보여준다.

| 이유 | 점수 |
|---|---|
| 마감 14일 이내 / 30일 이내 / 모집 중 | +30 / +20 / +10 |
| 모집 예정 / 상시 / 모집 종료 | +8 / +6 / −20 |
| 확인된 조건을 충족 | +30 |
| 코드 조건 충족(본문 미확인) | +14 |
| 확인 필요(사람이 확인한 정책 / 본문 미확인 정책) | +12 / +4, 남은 확인 사항 하나당 −2(최대 4개) |
| 공식 공고를 사람이 확인 | +25 |
| 기간 조건이 아직 남음 | −15 |
| 관심 분야(취업·창업) / 역량 강화 | +12 / +8 |
| 이 상태에서 새로 검토 대상(모집 종료·기간 조건이 남은 정책 제외) | +20 |

- **놓는 순서(리뷰 반영):** 사람이 공식 공고를 확인했고 모집이 열려 있는 정책을 먼저 놓고, 그 안에서 점수 순. 동점이면 확인된 정책, 마감이 가까운 정책, 정책 번호 순.
- **본문을 아무도 확인하지 않은 "확인 필요" 정책**은 자격 근거가 약하므로 마감 가점을 절반만 주고 관심 분야 가점은 주지 않는다. 검증 정책과 이름이 같은 미확인 항목(군·구가 따로 등록한 같은 사업)은 루트에서 접는다.
- **기간 조건이 남아 있으면 "조건상 해당"이라고 하지 않는다**(확인 필요, 사유 "기간 경과 후 재검토"). 최근 이력 질문에 "예"라고 답한 경우와 수료 직후가 여기에 해당한다.
- 화면에는 총점을 보여주지 않고 이유와 이유별 점수만 보여준다(총점이 추천 점수로 읽히지 않게).
- **정책 사이의 연결선은 원문 인용이 있는 것만 그린다.** 인용마다 출처가 공식 공고인지 온통청년 API의 정책 설명인지 표시하고, 루트에 나온 정책과 관련된 것만 보여준다.
- (처음 설계) **정책 사이의 연결선은 공고 인용이 있는 것만 그린다.** "이어짐"은 `data/route-links.json`(출처 주소와 확인일 포함), "제한"은 검증 정책의 제한 문구에서 만든다. 가중치로 정책과 정책을 잇지 않는다.

### 하지 않는 것
- 가중치는 어느 길이 더 낫다는 뜻이 아니고, 신청 결과를 예측하지 않는다. 화면 안내 문구와 이유 문구는 응답 검사(`lib/agent/guard.ts`)와 같은 금지 표현 검사를 테스트에서 통과해야 한다.
- 순서 매기기와 질문은 서버 코드가 한다. 사용자 정보는 외부 AI로 가지 않는다(7장 유지).

### 상담 질문
답하면 판정이 바뀌는 질문만 묻는다(`lib/agent/questions.ts`, 바뀔 수 있는 정책이 0개면 묻지 않는다). 영향 받는 정책이 많은 질문부터 하나씩 묻고, 답은 판정 계산에만 쓰며 저장하지 않는다.
- 국민취업지원제도에 참여 중인가요? → 청년도전의 제한이 "적용됨"으로 바뀐다.
- 최근 6개월 안에 취업했거나 교육·직업훈련에 참여한 적이 있나요? → 이력 정보가 없어 "확인 필요"이던 시간 조건이 충족/미충족으로 정해진다.

## 추가(2026-11-17, 2차): 시간 흐름 시뮬레이션

### 왜 바꿨나
상태 갈림길을 짧은 분기로 보여주니 시뮬레이션의 장점이 드러나지 않았다. 사용자가 원한 것은 시간이 흐르면서 내 정책이 열리고 닫히는 것을 지켜보는 화면이다. 화면의 루트는 이 시뮬레이션으로 대체했다(분기 계산 `lib/route/build.ts`는 정책 사이 관계 표시에 계속 쓴다).

### 무엇을 하나 (`lib/route/timeline.ts`)
- **가로축은 오늘부터 12개월.** 대전제는 상태 변화(수료·취업·사업자등록)이고, 그 시점을 개월 수로 조절한다. 수강 중이면 수료 예정일이 기준일, 아니면 오늘이 기준일이며 "기준일부터 N개월 뒤 취업/사업자등록"을 0~12개월로 고른다.
- **계산 지점**마다(달마다, 가정한 사건이 일어나는 날, 기간 조건이 풀리는 날, 검증 정책의 마감일과 그다음 날) 그날의 상태로 전체 판정을 다시 한다. 입력 프로필은 바꾸지 않는다.
- **정책마다 신청 구간**(조건상 비해당이 아니고, 모집 중이고, 기간 조건이 풀린 구간)의 시작일과 끝나는 이유(모집 마감 / 상태 변화)를 구한다. 번호는 구간이 시작되는 순서다.
- **줄로 보여주는 정책**: 사람이 확인한 정책 전부 + 본문 미확인 정책 중 코드 조건을 충족하는 것 최대 6개(오늘 열려 있는 것 3개, 가정한 상태 변화로 열리는 것 3개).
- **달마다**: 그때의 상태 이름, 그 달에 일어나는 일(가정한 사건, 구간의 시작과 끝), 그 달에 구간이 열려 있는 정책.

### 화면
한 달씩 넘기거나 흘려보기로 자동 진행한다. 큰 글씨의 연·월과 상태, 그 달에 일어나는 일, 그 달에 열려 있는 정책 카드, 접어 둔 전체 기간 막대.

### 하지 않는 것
- 현재 공고 기준의 계산이다. 데이터 기준일 이후의 새 공고·변경은 반영되지 않으며 화면에 그렇게 적는다.
- 언제 취업·창업하는 것이 낫다는 판단을 하지 않는다. 가정을 바꾸면 구간이 달라진다는 사실만 보여준다. 문구는 금지 표현 검사를 테스트에서 통과해야 한다.
- 80억 분의 1 같은 인생 시뮬레이션에서 "시간이 흐르며 지켜본다"는 형식만 참고했고, 그 작품의 이름·화면·내용은 쓰지 않았다.
